# s08 学习笔记：用具体例子理解上下文压缩

这份笔记配合 [code.py](code.py) 阅读。先看例子里“内容怎么变”，再回到代码看函数怎么实现。

每个例子都围绕三个问题展开：

1. 处理之前，工作记录里有什么？
2. 程序做了什么？
3. 处理之后，模型还能直接看到什么？原文在哪里？

文中的 `……` 表示为讲解省略的内容；简短路径是示意，实际代码通常会输出工作目录下的完整路径。用于说明大小的字符数是示例值，真正统计还包括消息结构等开销。

## 1. 先把 messages 理解成一叠工作记录

我们一直使用这个任务：

> 用户：“空密码也能登录，帮我修好，再补一个测试。”

假设 `auth.py` 里有这样一段简化代码，用来演示空密码判断：

```python
def can_login(password):
    return True
```

无论密码是什么都返回 `True`，所以空密码也能通过。

程序要完成任务，可能会经历这些步骤：

```text
用户提出任务
    ↓
模型决定读取 auth.py
    ↓
Python 程序读取文件，把内容交给模型
    ↓
模型分析问题，决定修改
    ↓
Python 程序修改文件
    ↓
模型决定运行测试
    ↓
Python 程序运行测试，把结果交给模型
    ↓
模型根据测试结果继续修改，或告诉用户已经完成
```

这些过程都需要留下记录。保存这份记录的变量叫 `messages`。

可以把它想成模型面前的一叠纸：

```text
第1张：用户让我做什么
第2张：我决定读取哪个文件
第3张：读出来的文件内容
第4张：我分析出了什么问题
第5张：我决定怎么修改
第6张：修改是否成功
第7张：测试结果是什么
……
```

本节代码每次请求模型继续工作时，都会通过 `messages` 把当时保留下来的会话记录传过去。

因此，用户虽然只说了一句话，工作记录却可能增加很多条。Agent 自己读取文件、修改代码、运行测试，也会不断产生记录。

### 1.1 必须分开的两件事：模型收到的消息、磁盘上的文件

```text
messages：这次发给模型看的工作记录。

磁盘：auth.py、测试文件、保存下来的旧记录等。
```

假设磁盘上有一个文件：

```text
/project/auth.py
```

如果 `messages` 里只有这个路径，模型就只能直接看到路径。

要看到文件正文，需要模型请求读取工具，由 Python 程序把文件内容读出来，再作为工具结果放进消息里。

**“原文仍在磁盘上”和“原文仍在模型当前收到的消息里”，是两回事。** 后面所有压缩方式都要区分这两件事。

### 1.2 这里的“压缩”具体做什么

本节主要通过三种变化，让发给模型的文字变少：

```text
变化一：
12,000 字符的工具结果正文
    ↓
“完整结果保存在 r1.txt。”
```

```text
变化二：
中间的31条消息
    ↓
“这31条消息已经归档，地址是 t1.jsonl。”
```

```text
变化三：
很长的排查过程
    ↓
“已定位问题，尚未修改，下一步修改并补测试。”
```

先记住这三种变化，再看下面各个场景。

## 2. 情况一：任务很短，完整保留所有内容

### 2.1 用户刚提出任务

为了容易阅读，先用中文表示每一条消息：

```text
messages = [
  用户：“空密码也能登录，帮我修好，再补一个测试。”
]
```

程序把这份记录发给模型。

### 2.2 模型决定读文件

模型回复的是一个工具调用，含义是：“读取 auth.py。”

程序先把这次回复加入记录：

```text
messages = [
  用户：“空密码也能登录，帮我修好，再补一个测试。”

  模型：调用 read_file("auth.py")
]
```

**模型提出读取请求，真正读取文件的是 Python 程序。**

### 2.3 程序读出文件，追加结果

读取完成后：

```text
messages = [
  用户：“空密码也能登录，帮我修好，再补一个测试。”

  模型：调用 read_file("auth.py")

  工具返回：
    def can_login(password):
        return True
]
```

下一次请求模型时，它就同时看到了：

1. 用户要修什么问题。
2. 自己刚才要求读取什么。
3. 文件里实际写了什么。

于是它可以继续判断：“这里直接返回 True，需要增加空密码检查。”

### 2.4 记录很小时，prepare 只检查，不改动

每次调用主模型前，程序都会运行 `prepare()`。

假设整份记录只有几百或几千字符，消息也很少：

```text
检查最新一批工具结果：没有太大。
检查消息数量：没有太多。
检查整体字符数：没有超限。

结果：原样交给模型。
```

**执行了 prepare，不代表一定会发生压缩。** 它首先负责判断当前有没有必要整理。

### 2.5 对应到真实的数据结构

“模型要求调用工具”在消息里叫 `tool_use`：

```python
{
    "role": "assistant",
    "content": [
        {
            "type": "tool_use",
            "id": "r1",
            "name": "read_file",
            "input": {"path": "auth.py"},
        }
    ],
}
```

“程序执行后返回内容”叫 `tool_result`：

```python
{
    "role": "user",
    "content": [
        {
            "type": "tool_result",
            "tool_use_id": "r1",
            "content": "def can_login(password):\n    return True",
        }
    ],
}
```

这里先看懂两个点就够了：

- `id="r1"` 和 `tool_use_id="r1"` 把调用与结果对应起来。
- 工具结果也使用 `role="user"`。所以看到 user 消息时，还要看里面是什么，不能直接认为它是用户新提出的任务。

一条消息的 `content` 还可以包含多个块。**消息的条数和工具结果的个数，要分别计算。**

## 3. 情况二：旧工具结果太长，把正文换成文件地址

对应函数：`micro_compact()`。

### 3.1 处理前：已经读过很多文件

为了查问题，模型先后拿到了这些结果：

| 结果 | 内容 | 示例大小 | 模型是否已经看过 |
| --- | --- | --- | --- |
| R1 | auth.py 的内容 | 12,000 字符 | 看过 |
| R2 | routes.py 的内容 | 12,000 字符 | 看过 |
| R3 | config.py 的内容 | 12,000 字符 | 看过 |
| R4 | users.py 的内容 | 12,000 字符 | 看过 |
| R5 | test_auth.py 的内容 | 12,000 字符 | 看过 |
| R6 | 刚返回的测试日志 | 1,000 字符 | 还没看过 |

这里把文件规模放大，是为了演示长任务中的上下文增长。

消息记录大致是：

```text
[
  用户任务

  模型：读取 auth.py
  工具：R1，完整正文，12,000 字符

  模型：读取 routes.py
  工具：R2，完整正文，12,000 字符

  模型：读取 config.py
  工具：R3，完整正文，12,000 字符

  模型：读取 users.py
  工具：R4，完整正文，12,000 字符

  模型：读取 test_auth.py
  工具：R5，完整正文，12,000 字符

  模型：运行测试
  工具：R6，完整日志，1,000 字符
]
```

结果正文合计 61,000 字符，再加上消息结构等开销，超过了本节设置的 50,000 字符限制。

消息数量只有十几条，所以不需要先按消息数量裁剪。接下来尝试缩短旧工具结果。

### 3.2 程序先划出保护范围

`micro_compact()` 会先区分已经看过和还没看过的结果。

在这个例子里：

```text
已经看过：R1 R2 | R3 R4 R5
                 └──最近3个已看过的结果，先保留

还没看过：R6，先保留
```

因此，当前优先考虑缩短的是 R1 和 R2。

这里的“看过”是程序根据消息顺序判断的：最近一次 assistant 回复之后才新增的工具结果，视为模型还没有读过。它是在管理发送记录，没有办法检查模型是否真正理解了每一个细节。

### 3.3 先保存 R1，再替换消息里的正文

原来的 R1：

```text
工具结果 R1：
  auth.py 的完整正文
  第1行……
  第2行……
  ……共12,000字符
```

程序先创建结果文件：

```text
磁盘新增：
.task_outputs/tool-results/r1.txt

文件内容：
R1 原来的全部12,000字符
```

然后把消息中的正文替换成：

```text
工具结果 R1：
  [Earlier tool result saved at .../r1.txt]
```

这句话的意思是：“较早的工具结果已保存到这个文件。”

如果还需要腾空间，接着处理 R2。

### 3.4 处理后：消息还在，里面的两份正文变短了

```text
[
  用户任务

  模型：读取 auth.py
  工具：R1，[完整结果保存在 r1.txt]

  模型：读取 routes.py
  工具：R2，[完整结果保存在 r2.txt]

  模型：读取 config.py
  工具：R3，完整正文，12,000 字符

  模型：读取 users.py
  工具：R4，完整正文，12,000 字符

  模型：读取 test_auth.py
  工具：R5，完整正文，12,000 字符

  模型：运行测试
  工具：R6，完整日志，1,000 字符
]
```

这组示例的总大小可以从约 62,000 字符降到约 38,000 字符。具体长度会受路径等文字影响。

**消息条数没变，工具调用与结果的对应关系没变，变化的是 R1、R2 的正文。**

这一步不需要额外调用模型，Python 保存文件、替换字符串就能完成。

### 3.5 如果后来又需要 R1 呢？

模型看到路径后，可以再调用：

```text
read_file(".../r1.txt")
```

程序读出结果文件，再把内容作为新的工具结果追加到消息中。

恢复过程就是：

```text
当前只看到旧结果的文件地址
    ↓
请求读取这个地址
    ↓
程序读文件
    ↓
新的工具结果带回正文
```

**模型之前看过，表示这份结果适合优先移走；移走后，下一次发给模型的记录里只有路径，需要重新读取才能拿回正文。**

### 3.6 容易弄错的两个细节

第一，微压缩按历史顺序处理符合条件的旧结果，先处理较早的；这里没有按正文大小排序。

第二，最近3个指的是“已看过的工具结果块”，不一定是3条消息。如果一条消息里同时有5个刚返回的结果，这5个都可能还没被模型看过，微压缩会先保护它们。

## 4. 情况三：刚返回的新结果就很大，留下预览和路径

对应函数：`fit_tool_results()`。

### 4.1 处理前：一份新结果就有60,000字符

假设模型读取了一个大文件：

```text
[
  用户任务

  模型：读取一个大文件，调用编号 large

  工具结果 large：
    完整正文，60,000 字符
]
```

模型还没看到这份正文，但它已经足以让消息超限。

### 4.2 为什么前面的步骤没处理掉它？

按实际执行顺序看：

```text
最新一批工具结果预算：
  这一批只有60,000字符，没有超过200,000，跳过。

按消息数量裁剪：
  消息很少，跳过。

检查整体大小：
  超过50,000，需要缩短。

微压缩：
  这是模型还没看过的新结果，先保护。
```

这就出现了矛盾：新结果需要给模型看，但完整正文又太大。

于是进入 `fit_tool_results()`。

### 4.3 程序做了什么

程序保存全部正文：

```text
.task_outputs/tool-results/large.txt

里面有原来的全部60,000字符。
```

然后把消息里的正文替换成路径和前1,000字符：

```text
<persisted-output>
Full output: .../large.txt
Preview:
原结果的前1,000个字符……
</persisted-output>
```

### 4.4 处理后，模型直接看到什么？

```text
[
  用户任务

  模型：读取一个大文件，调用编号 large

  工具结果 large：
    全文在 .../large.txt
    前1,000字符预览：……
]
```

60,000 字符的正文变成了一千多字符的消息，模型可以先判断结果的类型和开头内容，再决定是否继续读取或搜索保存文件。

这个例子通常在此就能降到阈值以内，无需生成摘要。

### 4.5 和微压缩放在一起比较

```text
较早、已经看过的结果：
  完整正文 → 文件路径

仍然太大的结果，包括刚返回的新结果：
  完整正文 → 文件路径 + 一小段预览
```

`fit_tool_results()` 会按结果正文从大到小尝试缩短。只有替换后的文本确实更短，才采用替换。

因此，**超过50,000字符不代表立即生成摘要**，程序会先尽力缩短工具结果。

## 5. 情况四：一次返回多个大结果，先控制这一批

对应函数：`tool_result_budget()`。

虽然这里放在后面讲，实际管线里它最先执行。

### 5.1 什么叫“一批工具结果”？

模型的一次回复可以同时提出多个工具调用：

```text
模型：
  读取 a.txt
  读取 b.txt
  读取 c.txt
```

Python 程序执行完这一批调用，把三个结果放进同一条 user 消息：

```text
一条消息：
  content = [
    a.txt 的工具结果
    b.txt 的工具结果
    c.txt 的工具结果
  ]
```

所以它们是“三个结果块、一条消息”。

### 5.2 处理前：这一批合计250,000字符

```text
a：120,000 字符
b： 90,000 字符
c： 40,000 字符

总计：250,000 字符
```

超过默认批次预算200,000字符。

### 5.3 程序从最大的结果开始转存

先处理 a：

```text
磁盘新增：
.task_outputs/tool-results/a.txt

文件内容：
a 的完整120,000字符
```

消息中的 a 变成：

```text
a：
  Full output: .../a.txt
  Preview:
  前2,000字符……
```

此时这批结果大致是：

```text
a：约2,000多字符的预览和路径
b：90,000字符，暂时原样
c：40,000字符，暂时原样

合计：约132,000字符
```

已经低于200,000，这一步停止。

### 5.4 为什么 b 和 c 还没转存？

这一步的判断分两层：

1. 先看这一批的总量是否超过200,000。
2. 如果超过，再从最大的结果开始，转存其中超过30,000字符的结果。

降到批次预算以内，就不继续处理剩下的结果。

因此，**30,000是这一步挑选可转存结果的条件，不代表所有超过30,000的结果一出现就马上转存。**

### 5.5 剩下132,000字符，整体不还是太大吗？

是的，后续仍然要继续检查。

```text
这一步的问题：
  最新这一批返回得是否太多？
  预算：200,000字符。

后面的整体检查：
  所有保留下来的会话记录合在一起，是否太大？
  阈值：50,000字符。
```

所以“批次处理结束”之后，还可能继续微压缩、缩短新结果，最后才考虑摘要。

还有一个边界：如果这一批总量超过200,000，但每个结果都不超过30,000，这一步会跳过这些结果，未必能把总量降到预算以内。后面的整体检查仍会处理上下文大小问题。

### 5.6 两种预览长度分别出现在哪里

```text
tool_result_budget：通常保留前2,000字符。

fit_tool_results：进一步缩短时，通常保留前1,000字符。
```

## 6. 情况五：消息越来越多，把中间一段搬走

对应函数：`snip_compact()`。

前面几种情况，重点是“某份结果的正文太长”。这次关注的是“消息数量太多”。

### 6.1 处理前：已经积累60条消息

```text
[
  消息1
  消息2
  消息3
  消息4
  ……
  消息59
  消息60
]
```

默认达到50条，就会尝试裁剪到约30条。这一步即使在总字符数不大时也可能触发。

### 6.2 先保存全部历史

程序把当前全部60条消息写入：

```text
.transcripts/transcript_xxx.jsonl
```

`.jsonl` 可以理解为“一行一条JSON记录”。这里一行保存一条消息。

下面把这个文件简称为 `t1.jsonl`。

### 6.3 处理后：保留开头、归档提示、近期消息

先不考虑工具配对时：

```text
处理前：

[消息1～3] [消息4～34] [消息35～60]
```

```text
处理后：

[消息1～3]
[31条消息已归档，地址：t1.jsonl]
[消息35～60]
```

数量是：

```text
开头3条
+ 归档提示1条
+ 最近26条
= 30条
```

实际归档提示的格式类似：

```text
[31 messages archived at .../t1.jsonl]
```

模型直接看到的是这个提示，消息4～34的具体内容需要到归档中读取。

**这一步没有请模型写摘要，它只是保存历史，再从当前消息列表里移走中间一段。**

### 6.4 为什么达到50条，却降到30条？

可以把它理解为给后续工作留出空位：

```text
达到50条 → 裁到约30条。
继续工作 → 32条、34条、36条……
再次达到50条 → 再整理。
```

如果每次只裁到49条，工作一小步又触发，容易反复写归档。

### 6.5 边界一：读取请求和读取结果要一起保留

假设原计划的切点在这里：

```text
消息34：模型调用 read_file("auth.py")，编号 r1
────────原计划从这里开始保留────────
消息35：r1 对应的文件内容
```

如果丢掉34，保留35，就只剩一个没有对应调用的工具结果，API 可能认为消息结构不合法。

所以程序会把34也带进来：

```text
保留消息34：读取请求。
保留消息35：对应结果。
```

开头的保留区域也要照顾这种配对关系。

因此，**30是裁剪目标，最终可能略多于30条。**

### 6.6 边界二：本轮任务如果被搬走，要补回来

假设这是一段持续很久的会话：

```text
消息1～3：更早的聊天。

消息10：
用户：“空密码也能登录，帮我修好，再补一个测试。”

消息11～60：Agent 为本轮任务进行的排查和修改。
```

裁剪消息4～34时，本轮任务原话也会被移走。

为了不让模型失去当前目标，程序单独保存了当前用户请求，参数名叫 `active_request`。

裁剪完成后，`prepare()` 会检查当前请求是否仍然可见；如果原话和对应的摘要请求标记都不存在，就补回：

```text
[
  消息1～3
  归档提示
  消息35～60

  用户：“空密码也能登录，帮我修好，再补一个测试。”
]
```

所以这一例可能是60条变成31条，而不是30条。

## 7. 情况六：前面的办法都不够，请模型写交接记录

对应函数：`compact_history()`。

### 7.1 什么时候会走到这一步？

工具结果可以转存，但消息里还可能有大量模型分析、讨论和任务说明。

例如：

```text
用户：空密码也能登录，帮我修好，再补一个测试。

模型：先检查认证逻辑……
工具：文件内容……

模型：可能是配置问题，我再检查配置……
工具：配置内容……

模型：配置没有问题，再看看路由……
工具：路由内容……

模型：经过排查，确认是 auth.py 的返回值问题……
……
```

即使把能缩短的工具结果处理掉，整份记录仍然超过50,000字符，就会生成摘要。

更直接的例子是：只有几条消息，但其中一条模型分析特别长。消息数量裁剪没触发，又没有足够的工具结果可缩短，也会走到这里。

### 7.2 可以把摘要理解成一份交接记录

```text
原来：
  一长串“怎么排查、排查过什么、为什么这么判断”的过程。

整理后：
  任务是什么，已经做到哪里，接下来还要做什么。
```

程序先保存当前历史，再额外调用一次模型，要求它整理事实状态，保留：

- 当前目标。
- 已经做出的决定。
- 涉及的文件。
- 剩余工作。
- 用户约束。

这次摘要调用的任务是整理记录，原始工作会在后续主模型调用中继续。

### 7.3 处理后的消息具体长什么样？

假设摘要结果是：

```text
已检查配置和路由，没有发现问题。
已确认 auth.py 的 can_login 直接返回 True。
还没有修改文件。
下一步：增加空密码检查，并补测试。
```

原来一长串消息会被替换成一条新的 user 消息：

```text
messages = [
  用户消息：
    [Compacted]

    Current user request:
    空密码也能登录，帮我修好，再补一个测试。

    Conversation summary (reference only):
    "已检查配置和路由，没有发现问题。
     已确认 auth.py 的 can_login 直接返回 True。
     还没有修改文件。
     下一步：增加空密码检查，并补测试。"

    Full transcript: .../t1.jsonl
]
```

英文标签可以直接翻译为：

```text
Current user request：当前用户请求。
Conversation summary (reference only)：历史摘要，仅作参考。
Full transcript：完整历史的保存路径。
```

下一次主模型调用看到这一条，就能从“修改文件”继续工作。

### 7.4 为什么把当前请求与摘要分开？

因为摘要可能遗漏内容。

例如用户原话是：

```text
修好空密码问题，再补一个测试。
```

摘要却只写了：

```text
需要修复登录问题。
```

“补测试”这个要求就漏了。

代码通过 `active_request` 保存本轮用户原话，再单独写入压缩后的消息，减少对摘要准确复述任务的依赖。

另外，工具结果也使用 `role="user"`。如果直接把最后一条 user 消息当成当前任务，很可能拿到的是测试日志。因此当前请求需要在用户输入时明确传进来。

系统提示还要求把历史摘要当参考资料，当前用户请求单独作为任务依据。旧日志、旧对话里出现的文字，不应自动变成新的任务指令。

### 7.5 和“中间历史归档”有什么区别？

```text
snip_compact 之后：
  “旧记录保存在 t1.jsonl。”
  模型知道去哪里找，但提示里没有概括旧记录做了什么。

compact_history 之后：
  “已定位 auth.py 的问题，尚未修改，下一步修改并补测试。”
  模型直接拿到一份整理后的工作状态。
```

摘要方便接着工作，但会额外产生一次模型调用，也可能遗漏细节，所以在前面的处理仍不够时使用。

## 8. 情况七：模型主动调用 compact

### 8.1 为什么没超限也能压缩？

自动检查只知道消息多不多、文字长不长。模型还可以在一个阶段结束后主动提出：

```text
排查已经完成，现在整理一下记录，再进入修改和测试阶段。
```

它会调用一个名为 `compact` 的工具。

这个入口不要求当前已经超过50,000字符，最终同样调用 `compact_history()`。

### 8.2 一次响应可能同时包含 compact 和普通工具

例如模型一次回复提出：

```text
调用1：compact，编号 c1。
调用2：write_file，编号 w1，写入修改后的 auth.py。
```

看到 `compact` 时，程序先记下来：

```python
compact_requested = True
```

意思是：“这批工具都执行完以后，要整理一次记录。”

然后继续执行 `write_file`。

### 8.3 先追加这一批的全部结果

执行完成后，消息里先出现：

```text
模型：
  请求 compact，c1。
  请求 write_file，w1。

工具结果：
  c1：已收到整理请求，本批执行后压缩。
  w1：auth.py 已成功写入。
```

接着才生成摘要。

摘要可以准确记录：

```text
auth.py 已经加入空密码检查。
下一步运行测试。
```

如果在写入之前就整理，记录里只能写“准备修改”，不能根据那份摘要确认写入是否已经发生。

**这个顺序让本批工具调用及其结果都进入归档和摘要，避免在执行状态不完整时就替换历史。**

即使本批出现多个 `compact` 调用，程序也通过这个布尔标记，在整批结果追加后统一整理。

## 9. 情况八：程序觉得够短，API 仍然拒绝

对应函数：`reactive_compact()`。

### 9.1 为什么本地检查通过，还可能报“太长”？

本节估算方法是：

```python
len(json.dumps(messages, default=str, ensure_ascii=False))
```

也就是把消息转换成JSON文字，再数有多少字符。

例如：

```text
"abc" 有3个字符。
"登录" 有2个字符。
```

实际估算还包含JSON里的字段名、引号和其他结构文字。

模型API按token等请求条件限制大小，字符数只能粗略估计。本地这段统计也没有包含单独传入的系统提示和工具定义等全部请求内容。

因此可能发生：

```text
prepare：本地检查结束。
    ↓
请求模型。
    ↓
API：prompt is too long。
```

### 9.2 收到过长错误后，再补救一次

假设当前有12条消息：

```text
[较早的7条] [最近的5条]
```

`reactive_compact()` 先保存完整12条，再总结较早7条，保留最近5条：

```text
[
  新消息：
    当前用户任务
    较早7条的摘要
    完整历史路径

  最近的第1条，原样
  最近的第2条，原样
  最近的第3条，原样
  最近的第4条，原样
  最近的第5条，原样
]
```

### 9.3 为什么保留最近的消息？

例如最新工具结果是：

```text
测试失败：
AssertionError:
空密码应该返回 False，实际返回 True。
```

保留这段原文，后续模型就能直接看到眼前需要解决的报错。

所以它和普通自动摘要的形态有区别：

```text
compact_history：
  当前历史 → 一条“当前任务 + 历史摘要 + 路径”的新消息。

reactive_compact：
  旧部分 → 摘要。
  最近部分 → 通常保留约5条原消息。
```

### 9.4 几个边界

- 如果保留最近5条的切点会拆开工具调用和结果，就往前多保留一条，因此可能留下6条近期消息。
- 如果总共不超过5条，代码会总结全部历史，只返回一条新消息，不再另拼近期原消息。
- 连续过长失败最多补救重试一次；重试仍失败，就抛出异常。
- 一次主模型调用成功后，重试计数会清零。因此限制的是连续失败补救次数。
- 网络故障等无关异常不会触发这条补救逻辑，而会继续向外抛出。

流程可以这样记：

```text
第一次请求 → API说太长
    ↓
保存历史，总结旧部分，保留近期消息
    ↓
回到循环，重新prepare，再请求
    ├─ 成功：继续任务，重试计数清零
    └─ 仍然失败：抛出错误
```

## 10. 把这些例子放回实际执行顺序

前面为了容易理解，先讲了“旧结果怎么缩短”，再讲批次预算。实际每次主模型调用前，顺序如下：

```text
开始下一次主模型调用前的准备
    ↓
tool_result_budget
  最新这一批工具结果超过200,000字符？
  → 尝试从最大的结果开始转存，留下预览和路径。
    ↓
snip_compact
  消息达到50条？
  → 保存历史，保留开头和近期，把中间换成归档提示。
    ↓
如果裁剪移走了当前用户任务，就补回任务原话。
    ↓
检查整份messages的字符数
    ├─ 不超过50,000：直接请求模型。
    └─ 超过50,000：继续。
           ↓
       micro_compact
         → 缩短较早、已看过的工具结果，保留路径。
           ↓
       仍超过50,000？
           ├─ 否：请求模型。
           └─ 是：fit_tool_results
                    → 优先缩短最大的结果，包括新结果，留下预览和路径。
                      ↓
                  仍超过50,000？
                      ├─ 否：请求模型。
                      └─ 是：compact_history
                               → 保存历史，请模型生成摘要，再继续主调用。
```

另外两个入口在管线外：

```text
模型主动调用compact
    → 执行完本批工具并追加全部结果
    → compact_history

主模型API报上下文过长
    → reactive_compact
    → 回到循环重试一次
```

第一步和第二步每轮都会检查，后续几个缩短阶段按条件执行。

## 11. 复习时容易混淆的细节

### 11.1 “40,000”是努力达到的目标，“50,000”是继续升级处理的判断线

代码会计算：

```python
target = int(50000 * 0.8)  # 40,000
```

意思是：既然已经开始腾空间，就希望多腾一些，给后续记录留余地。

但进入下一层处理时，判断的仍然是是否超过50,000。

例如微压缩结束后剩45,000字符：

```text
还没达到40,000的目标。
但已经不超过50,000。
因此可以继续请求模型，无需强行进入下一层。
```

### 11.2 完整转存，指的是压缩器当时拿到的内容

如果读取工具把全文交给压缩器，结果文件就能保存那份全文。

但工具自身也可能先限制输出。例如本节 `run_bash()` 最多返回前50,000字符，`read_file` 也可以通过参数限制行数。

压缩器只能保存它收到的结果，无法补回工具之前已经省略的部分。

同理，后续归档保存的是“当时的消息列表”。如果更早的压缩已经把正文替换为路径，新的归档里保存的也会是路径；原正文仍需到对应结果文件中读取。

### 11.3 生成摘要，也有输入长度限制

摘要调用本身也需要控制输入。

历史序列化文本超过80,000字符时，本节会取：

```text
开头20,000字符
+ 中间省略提示
+ 末尾60,000字符
```

再交给摘要模型。省略提示本身会多占少量字符，因此这不是严格的80,000字符硬上限。

这也意味着摘要模型未必直接看到了所有中间细节。完整历史已经先保存到磁盘，但摘要请求里只放入了这份截取文本。

### 11.4 压缩是尽力缩短，不保证任何输入都一定能装下

例如用户当前请求本身特别长，或者保留的近期消息仍然很大，压缩后依旧可能失败。

本节通过自动整理和一次API错误补救处理常见情况，但没有保证所有输入都能被成功发送。

### 11.5 这里处理的是当前会话上下文

这些文件帮助当前长任务恢复被移走的细节。s09 的持久记忆会进一步讨论哪些信息需要跨会话保存和检索。

## 12. 快速复习表

| 看到的函数名 | 可以读成什么 | 处理后模型直接看到什么 | 是否额外调用摘要模型 |
| --- | --- | --- | --- |
| `tool_result_budget` | 最新这一批太大，先搬走大结果 | 预览和路径，其余结果可能原样保留 | 否 |
| `snip_compact` | 消息太多，把中间搬走 | 开头、归档提示、近期消息 | 否 |
| `micro_compact` | 较旧结果占地方，先换成地址 | 旧结果的路径，受保护结果仍有正文 | 否 |
| `fit_tool_results` | 还是太大，连新结果也可以缩短 | 大结果的预览和路径 | 否 |
| `compact_history` | 写一份交接记录 | 一条包含当前请求、历史摘要和路径的新消息 | 是 |

## 13. 用几个小问题检查自己是否理解

### 问题一：只返回一份60,000字符的新文件，会立刻生成摘要吗？

通常不会。

```text
批次预算：60,000没有超过200,000，先跳过。
消息裁剪：消息很少，跳过。
整体大小：超过50,000。
微压缩：新结果还没看过，先保护。
进一步缩短：保存全文，保留前1,000字符预览和路径。
```

这时通常已经够短，无需调用摘要模型。

### 问题二：模型之前看过一份文件，微压缩后还能直接看到全文吗？

如果全文已经被替换为路径，下一次模型直接看到的就是路径。它可以重新调用工具读取，拿回正文。

### 问题三：60条短消息，总共只有10,000字符，还会整理吗？

会。消息达到50条，会触发 `snip_compact()`；这个步骤独立检查消息数量。

### 问题四：微压缩后剩45,000字符，会继续生成摘要吗？

不会因为这个大小继续摘要。它已经不超过50,000，虽然还没达到40,000的缩短目标，也可以继续请求模型。

### 问题五：一条响应里先compact、再写文件，程序会先压缩吗？

不会立即压缩。它先标记稍后整理，执行完本批调用，追加所有结果，再统一摘要。

### 问题六：归档提示和历史摘要分别告诉模型什么？

```text
归档提示：告诉它旧记录在哪里。

历史摘要：告诉它之前做到了哪里，接下来还要做什么。
```

## 14. 回到源码时，从哪里看起

建议按这个顺序查找函数名：

1. `prepare()`：把前面的处理串起来，判断什么时候进入下一层。
2. `agent_loop()`：看整理完的消息如何发给模型、工具结果如何追加回来，以及API报错后怎么重试。
3. `micro_compact()` 和 `fit_tool_results()`：对照“完整正文变成路径或预览”的例子。
4. `snip_compact()`：对照“60条变成约30条”的例子。
5. `compact_history()` 和 `reactive_compact()`：对照两种交接记录的形态。

先跟踪 `messages` 在每个函数执行前后长什么样，再研究路径验证、文件命名、循环写法等实现细节。
