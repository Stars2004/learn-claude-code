> 把耗时命令交给后台运行，让 Agent 先做其他不依赖结果的工作，之后再把命令结果交给模型。

## 1. 贯穿全篇的例子：跑测试期间阅读 README

假设用户提出：

> “运行注册功能的测试。等待测试期间，帮我读一下 README，看看测试说明写得是否清楚。”

这里有两件事：

```text
事情一：运行 pytest -q，可能比较慢。

事情二：读取 README.md，通常比较快。
```

阅读 README 不需要先知道测试有没有通过，因此可以在测试运行期间进行。

本节要让下面两条工作线交错进行：

```text
主流程：
启动测试 → 收到启动编号 → 阅读 README → 继续独立工作 → 收集结果

后台：
       └──────── 执行 pytest ────────→ 保存结果
```

先记住：**提前返回的是“启动回执”，真正的测试结果稍后才来。**

## 2. 先看同步执行：为什么 Agent 会卡在慢命令上

### 2.1 同步执行的顺序

假设模型提出：

```text
先执行 pytest -q。
然后读取 README.md。
```

同步执行大致是：

```text
Python 开始运行 pytest
    ↓
等待测试结束
    ↓
拿到测试结果
    ↓
再读取 README.md
    ↓
把工具结果交给模型
```

如果测试运行30秒，在这段时间里：

| 位置 | 正在发生什么 |
| --- | --- |
| 测试进程 | 正在执行测试 |
| Agent 主流程 | 等待当前命令返回 |
| 后面的读取 README | 尚未执行 |

主流程中的这次工具调用没有返回，后续步骤就还没轮到。

可以想成：

```text
把衣服放进洗衣机。
一直站在旁边等洗完。
然后才去整理书桌。
```

整理书桌不依赖洗衣结果，这段等待可以被利用起来。

### 2.2 后台执行改变的是等待的位置

后台方式：

```text
主流程启动后台命令
    ↓
很快收到“已启动”的回执
    ↓
继续读取 README
```

等待命令结束的工作交给后台线程：

```text
后台线程启动 Shell 命令
    ↓
等待命令结束
    ↓
保存结果，等待主流程收集
```

命令不一定跑得更快，但主流程可以利用它运行期间的时间。

### 2.3 和 s10 任务账本的区别

| 章节 | 主要解决什么 | “运行测试”这个例子里做了什么 |
| --- | --- | --- |
| s10 Task System | 保存任务状态、负责人和依赖 | 创建一张“需要运行测试”的任务卡片 |
| s11 Background Tasks | 后台运行具体命令，之后交回结果 | 真正启动 `pytest -q`，暂时不等最终输出 |

s10 创建任务记录，本身不会自动执行测试。s11 的后台命令执行才会真正启动相应进程。

## 3. 情况一：明确请求后台执行

### 3.1 模型发出什么请求

```json
{
  "type": "tool_use",
  "id": "call_test_1",
  "name": "bash",
  "input": {
    "command": "pytest -q",
    "run_in_background": true
  }
}
```

字段解释：

| 字段 | 含义 |
| --- | --- |
| `id` | 这一次工具调用的编号，用于和工具返回配对 |
| `name` | 要使用 `bash` 工具 |
| `command` | 要执行的 Shell 命令 |
| `run_in_background` | 是否明确请求后台执行 |

### 3.2 程序怎样判断

对应函数：`should_run_background()`。

```python
def should_run_background(tool_name: str, tool_input: dict) -> bool:
    return (
        tool_name == "bash"
        and tool_input.get("run_in_background") is True
    )
```

这里同时要求：

```text
工具名必须是 bash。

run_in_background 必须明确是布尔值 True。
```

### 3.3 几种情况放在一起看

| 调用情况 | 是否进入后台路径 |
| --- | --- |
| bash，明确设置 `true` | 是 |
| bash，没有设置这个参数 | 否，仍同步执行 |
| bash，设置 `false` | 否，仍同步执行 |
| read_file，即使附带这个标记 | 不会因此进入后台路径 |

JSON 中的 `true` 对应 Python 的 `True`。字符串 `"true"` 不是这里要求的布尔值。

程序不会通过 `install`、`build`、`test` 等词猜测命令是否应该后台运行。

例如：

```json
{
  "command": "npm install"
}
```

虽然安装可能很慢，没有明确设置后台参数，这份代码仍会同步执行。

**“可能很慢”和“已请求后台执行”要分开。**

## 4. 后台分流发生在哪里：先检查权限，再决定执行方式

对应入口：`execute_tool()`。

执行顺序可以读成：

```text
收到工具调用
    ↓
PreToolUse：权限检查和日志等
    ↓
是否被拒绝？
    ├─ 是：返回拒绝信息，不启动后台任务。
    └─ 否：继续判断是否请求后台。
               ├─ 是：交给 BackgroundManager.start。
               └─ 否：通过 call_tool 同步执行。
    ↓
PostToolUse
    ↓
返回当前工具结果
```

所以后台执行不会绕过权限检查：

```text
先判断这条命令能不能执行。
再决定以同步还是后台方式执行。
```

如果 `PreToolUse` 返回了拒绝信息，本次调用在分流之前就结束了，后台登记表中不会因此新增任务。

在后台启动路径中，`PostToolUse` 收到的是“后台已启动”的回执。最终命令结果会通过后面的通知传递，当前代码不会为最终结果再自动触发一次相同的 `PostToolUse`。

## 5. 情况二：启动后台命令后，内存里多了什么

### 5.1 先认识 BackgroundManager 的三个容器

```python
class BackgroundManager:
    def __init__(self):
        self.tasks = {}
        self.results = {}
        self._ready = []
        self._counter = 0
        self._lock = threading.Lock()
```

可以把它理解成“后台命令登记处”：

| 容器 | 通俗理解 | 保存什么 |
| --- | --- | --- |
| `tasks` | 后台任务登记表 | 命令、原调用编号、当前状态 |
| `results` | 已完成结果柜 | 后台编号对应的结果文字 |
| `_ready` | 待领取名单 | 哪些后台命令已经结束，可以发通知 |

`_counter` 用来依次分配编号；`_lock` 用来保护多个线程共同访问的内部记录。

### 5.2 处理前

```python
tasks = {}
results = {}
_ready = []
```

没有后台命令，也没有待领取结果。

### 5.3 start 先登记任务

收到 `pytest -q` 的后台请求后，先分配编号：

```text
bg_0001
```

再登记：

```python
tasks = {
    "bg_0001": {
        "tool_use_id": "call_test_1",
        "command": "pytest -q",
        "status": "running"
    }
}
```

假设命令此时还没结束：

```python
results = {}
_ready = []
```

读成人话：

```text
有一条编号 bg_0001 的测试命令正在运行。
它来自 call_test_1 这次工具调用。
现在还没有最终结果，也没有完成通知可领。
```

### 5.4 两个 ID 的用途不同

```text
call_test_1：会话里这一次工具调用的编号。

bg_0001：后台管理器给命令分配的编号。
```

任务记录通过 `tool_use_id` 保存了二者的关联，但它们不是同一类编号。

本节的 `bg_0001` 也不同于 s10 的 `task_a1b2c3d4`：前者是当前进程里的后台命令编号，后者是持久任务卡片编号。

### 5.5 编号不是持久身份

当前 `_counter` 从0开始递增，格式化成 `bg_0001`、`bg_0002` 等。

它没有保存到文件，重启后重新从新管理器的计数开始，不能当作跨进程永久唯一的任务身份。

## 6. 后台到底是谁在跑：主线程、后台线程、Shell 进程

### 6.1 启动线程的代码

```python
thread = threading.Thread(
    target=self._run,
    args=(task_id, command),
    daemon=True,
)

thread.start()
```

先用简单的理解：原来的 Python 主流程继续走，另开一条执行路线等待这条命令的结果。

### 6.2 三个角色分别做什么

```text
主线程：
  运行 Agent Loop。
  调用模型。
  执行其他工具。
  收集后台完成通知。

后台线程：
  调用命令执行函数。
  等待命令结束。
  保存结果和状态。

Shell 命令进程：
  真正执行 pytest、构建、安装等具体命令。
```

对应关系：

```text
主线程启动后台线程
    ↓
后台线程执行 _run
    ↓
_run_bash_process 通过 subprocess.Popen 启动命令
    ↓
后台线程等待并收集命令输出
    ↓
结果写回管理器
```

后台线程通常是在等待外部命令，不是再启动一个语言模型 Agent。

**模型仍然负责决策；后台 worker 负责执行命令和交回结果。**

### 6.3 快命令可能很快就完成

`start()` 先登记，再启动线程，最后返回编号。线程启动后马上有机会运行。

如果命令很快，主流程拿到“已启动”的回执时，后台状态可能已经是 `completed`。

下面把 `running` 和完成阶段分开，是为了讲清变化，不表示每次都能观察到一段很长的运行中状态。

### 6.4 线程启动失败怎样处理

如果 `thread.start()` 抛出异常，代码会移除刚登记的任务，再由工具入口返回错误文字。

这种情况连后台 worker 都没有正常启动；要和“命令已经运行，但最后失败”分开。

## 7. 情况三：原始工具调用先收到启动回执

### 7.1 execute_tool 很快返回什么

启动成功后，返回文字：

```text
[Background task bg_0001 started] The result will be collected on a later turn.
```

意思是：

> 后台命令 bg_0001 已启动，结果会在后面的轮次收集。

### 7.2 Agent Loop 把它作为 tool_result 加进消息

```json
{
  "role": "user",
  "content": [
    {
      "type": "tool_result",
      "tool_use_id": "call_test_1",
      "content": "[Background task bg_0001 started] The result will be collected on a later turn."
    }
  ]
}
```

这份结果已经回应了 `call_test_1` 这次工具调用。

此时模型知道的是：

```text
我提出运行测试。
程序接受并启动了后台命令。
后台编号是 bg_0001。
当前还没有拿到测试通过或失败的结论。
```

### 7.3 启动成功，不等于测试成功

```text
启动回执：
  表示后台命令已安排启动。

最终结果：
  后面才知道成功、失败或超时。
```

模型不能仅凭“started”就向用户断言测试通过。

## 8. 情况四：测试还在跑，Agent 继续读取文件

### 8.1 收到启动回执后的消息

```text
[
  用户：运行注册测试，期间阅读 README。

  模型：调用 bash，后台运行 pytest -q。

  工具：bg_0001 已启动，稍后收集结果。
]
```

主流程进入下一轮模型调用。

### 8.2 模型决定读取 README

工具调用可以读成：

```text
read_file("README.md")
```

程序正常读取文件，追加结果：

```text
[
  用户：运行注册测试，期间阅读 README。

  模型：调用 bash，后台运行 pytest -q。

  工具：bg_0001 已启动，稍后收集结果。

  模型：读取 README.md。

  工具：README 的文件内容……
]
```

同一时间，后台命令仍然可以继续运行。

```text
主流程：
  已拿到 README，可以检查说明。

后台：
  pytest 可能仍未结束。
```

### 8.3 不意味着所有工具都自动并行

当前实现只给 bash 增加了显式后台执行路径。

普通文件工具仍按当前执行流程处理；主循环中同一批工具调用也还是逐个分发。

```text
后台 bash：
  启动后不等最终结果，就能继续处理后续工具。

同步 bash：
  仍会等待命令结果，后续调用还要等它返回。
```

所以，同一批调用里如果先安排了一个同步慢命令，排在它后面的后台启动请求仍要等前面的调用结束。

## 9. 情况五：后台命令完成以后，三个容器怎么变

### 9.1 假设测试成功结束

```text
命令：pytest -q

输出：3 passed in 0.30s

退出码：0
```

`_run()` 根据退出码判断状态：

```python
status = "completed" if exit_code == 0 else "failed"
```

### 9.2 tasks 更新状态

```python
tasks = {
    "bg_0001": {
        "tool_use_id": "call_test_1",
        "command": "pytest -q",
        "status": "completed"
    }
}
```

### 9.3 results 保存结果

```python
results = {
    "bg_0001": "3 passed in 0.30s"
}
```

### 9.4 _ready 登记可领取编号

```python
_ready = ["bg_0001"]
```

可以这样读：

```text
tasks：这条命令已经结束。
results：这是它的结果。
_ready：现在可以通知主流程领取。
```

**此时结果已经在 Python 内存里，但模型未必已经看到了。**

后台线程不会因此直接发起模型调用，也不会把内容插入模型当前正在生成的回答。

## 10. 情况六：主流程领取结果，生成完成通知

### 10.1 什么时候收集

Agent Loop 开头是：

```python
while True:
    inject_background_results(messages)
    response = client.messages.create(...)
```

也就是：

```text
准备再次请求模型
    ↓
先检查后台完成结果
    ↓
有结果就加入messages
    ↓
再请求模型
```

这里的“下一轮”不一定要用户重新输入。只要当前 Agent 还在继续调用工具，内部下一次循环就有机会收集。

### 10.2 collect 取出完成项

`inject_background_results()` 会调用：

```text
collect_background_results()
    ↓
BACKGROUND.collect()
```

`collect()` 读取 `_ready`，取出对应任务信息和结果，生成通知。

### 10.3 通知具体长什么样

```xml
<task_notification>
  <task_id>bg_0001</task_id>
  <status>completed</status>
  <command>pytest -q</command>
  <summary>3 passed in 0.30s</summary>
</task_notification>
```

逐项翻译：

| 字段 | 意思 |
| --- | --- |
| `task_id` | 哪条后台命令结束了 |
| `status` | 是正常完成还是失败 |
| `command` | 原来执行了什么 |
| `summary` | 结果文字的前一部分 |

这是便于模型识别的文本格式。它以 `text` 块加入对话，没有新增一个叫 `task_notification` 的 API 消息角色。

## 11. 情况七：把完成通知追加到 messages

### 11.1 最后一条 user 消息是工具结果列表

注入前，假设最后一条消息是读取 README 的结果：

```json
{
  "role": "user",
  "content": [
    {
      "type": "tool_result",
      "tool_use_id": "call_read_1",
      "content": "README 的文件内容……"
    }
  ]
}
```

注入后，保留原结果，再追加普通文本块：

```json
{
  "role": "user",
  "content": [
    {
      "type": "tool_result",
      "tool_use_id": "call_read_1",
      "content": "README 的文件内容……"
    },
    {
      "type": "text",
      "text": "<task_notification>\n  <task_id>bg_0001</task_id>\n  <status>completed</status>\n  <command>pytest -q</command>\n  <summary>3 passed in 0.30s</summary>\n</task_notification>"
    }
  ]
}
```

因此下一次主模型同时看到：

```text
刚读取的 README 内容。

后台测试已经完成，结果是3 passed。
```

它可以继续判断：测试已经通过，README 的说明是否需要补充。

### 11.2 最后一条 user 消息是字符串

注入前：

```json
{
  "role": "user",
  "content": "继续看看测试结果。"
}
```

注入后：

```json
{
  "role": "user",
  "content": [
    {
      "type": "text",
      "text": "继续看看测试结果。"
    },
    {
      "type": "text",
      "text": "<task_notification>后台任务完成通知，详细字段见前面的示例。</task_notification>"
    }
  ]
}
```

原来的用户输入会转换成一个文本块，内容保留。

### 11.3 如果最后不是 user 消息

函数还有一个备用分支：追加一条新的 user 消息，里面放通知文本块。

在当前教学循环的正常用法中，来到下一次模型调用前，末尾通常已经是用户输入或刚追加的工具结果消息，因此主要使用前两种分支。

### 11.4 返回值是什么

`inject_background_results()` 返回这次注入的通知数量。

```text
没有结果：返回0，不改消息。

有一份结果：追加一个通知块，返回1。

有多份结果：追加多个通知块，返回对应数量。
```

## 12. 为什么完成通知不再复用原来的 tool_use_id

启动时，原始调用已经得到了工具结果：

```text
模型工具调用：call_test_1。

对应tool_result：bg_0001已启动，稍后收集。
```

如果完成后再追加一次：

```text
tool_result：
  tool_use_id = call_test_1
  内容 = 测试通过
```

同一次工具调用就会出现第二份工具结果，破坏正常的调用与结果配对方式。

当前设计分成两种消息：

```text
启动回执：
  tool_result。
  回应这一次启动请求。

最终完成通知：
  text。
  作为之后发生的独立事件，带后台编号说明结果。
```

虽然后台登记信息里保存了原始 `tool_use_id`，最终通知没有把它用作第二个 `tool_result` 的配对编号。

可以这样记：

```text
call_test_1：启动请求已经回应过。

bg_0001：后续用来识别是哪条后台命令完成。
```

## 13. 情况八：只领取一次，之后会清理记录

### 13.1 领取之前

```python
tasks = {
    "bg_0001": {
        "tool_use_id": "call_test_1",
        "command": "pytest -q",
        "status": "completed"
    }
}

results = {
    "bg_0001": "3 passed in 0.30s"
}

_ready = ["bg_0001"]
```

### 13.2 collect 取走后

假设没有其他后台命令：

```python
tasks = {}
results = {}
_ready = []
```

取出的结果已经变成通知字符串，随后由 `inject_background_results()` 加入消息。

### 13.3 再收集不会重复追加

```text
第一次collect：
  返回bg_0001的完成通知。

第二次collect：
  没有新的完成项，返回[]。
```

所以 `collect()` 是消费待领取结果，不是只看一眼状态。

如果直接调用它把通知取出来，需要使用这次返回的通知；不能忽略返回值，再期待后面的注入函数从队列中重新领取同一份结果。

### 13.4 后台队列只追加一次，历史消息仍保留

```text
后台队列：
  同一份结果只被领取一次。

messages：
  已加入的通知作为历史保留。
  后续请求模型时，历史里仍可能包含它。
```

“不重复通知”指不反复追加同一个事件，不表示模型后续再也不会收到这段历史。

### 13.5 多个后台命令的结果顺序

假设先启动：

```text
bg_0001：较慢的测试。
bg_0002：较快的独立检查。
```

如果第二项先结束，可能是：

```python
_ready = ["bg_0002"]
```

它可以先被领取，不必等 bg_0001。

如果两项都结束了，名单主要反映完成登记的顺序；不能假定通知总是按启动编号顺序到达。应根据通知中的 `task_id` 和 `command` 对应结果。

## 14. 情况九：命令失败、超时或 worker 异常

### 14.1 测试正常运行，但最后失败

假设命令返回：

```text
输出：FAILED test_empty_password

退出码：1
```

`_format_bash_result()` 会加上非零退出码提示：

```text
Error: command exited with status 1
FAILED test_empty_password
```

后台状态是：

```text
failed
```

最终通知例如：

```xml
<task_notification>
  <task_id>bg_0002</task_id>
  <status>failed</status>
  <command>pytest -q</command>
  <summary>Error: command exited with status 1
FAILED test_empty_password</summary>
</task_notification>
```

主模型看到以后，可以再检查失败用例、修改代码、重新运行验证。

### 14.2 状态主要看退出码，不分析 passed 这个词

```text
exit_code == 0 → completed。

其他值，包括None → failed。
```

这份代码不会理解整份测试报告来判断业务是否真的正确。命令是否正确表达了验证目标，仍然重要。

### 14.3 放到后台，仍然有120秒超时

实际执行函数中使用：

```python
stdout, stderr = process.communicate(timeout=120)
```

超过时间，返回：

```text
Error: Timeout (120s)
```

退出码位置返回 `None`，所以后台状态是 `failed`。

通知大致是：

```xml
<task_notification>
  <task_id>bg_0003</task_id>
  <status>failed</status>
  <command>某条耗时命令</command>
  <summary>Error: Timeout (120s)</summary>
</task_notification>
```

**后台执行让主流程可以继续，但没有自动放宽命令超时。**

### 14.4 exit_code 为 None，为什么格式函数没有再加状态码前缀

`_format_bash_result()` 对 `0` 或 `None` 都直接返回已有输出文字。

超时、部分启动错误的输出本身已经是 `Error: ...`，不需要再拼一个“退出码None”的提示。

不要由此推断 `None` 代表成功；后台成功与否仍由 `_run()` 的 `exit_code == 0` 判断。

### 14.5 worker 执行中抛异常

`_run()` 捕获普通异常后，把结果写成：

```text
Error: 异常类型: 具体信息
```

并标记 `failed`，加入待领取队列。主流程之后仍能通过相同的通知路径读到失败信息。

这和“后台线程没有启动成功”是两个不同阶段的失败。

## 15. 情况十：命令结束后，会自动把 Agent 叫醒吗

**当前实现不会主动唤醒。** 结果收集发生在循环顶部，不是后台线程自动调用模型。

### 15.1 当前任务还在继续循环

```text
启动后台测试。
模型继续要求读取文件。
程序返回文件结果。
再次进入循环顶部。
收集已经完成的后台通知。
再调用模型。
```

这种情况下，不需要用户重新输入，也有机会收到结果。

### 15.2 模型已经结束本轮回答

```text
启动后台测试。
    ↓
模型说“测试已经启动，稍后查看”。
    ↓
没有新的工具调用，Stop Hook也没有要求继续。
    ↓
Agent Loop返回。
    ↓
CLI等待用户输入。
    ↓
后台测试之后才结束。
```

这时后台只会更新 `results` 和 `_ready`。

程序不会因为 `_ready` 多了一项，就自动再请求一次模型。

用户输入：

> “继续看看测试结果。”

再次进入 Agent Loop，才会先注入通知，再请求模型。

### 15.3 模型调用期间完成，也不会插进已经发出的请求

```text
主流程已经发起模型请求。
后台命令在此期间结束。
```

这份结果等待之后再次进入循环顶部才会被收集，不会直接改变已经发出的那次请求。

如果主模型接着返回最终文本并结束本轮，也可能要等下一次用户输入。

### 15.4 三个时间点分开记

```text
命令结束。
    ↓
结果写入管理器，等待领取。
    ↓
通知加入messages，发给模型。
```

这三个阶段不一定同时发生。

## 16. 哪些工作适合后台，哪些必须等待

系统提示要求只对独立的 Bash 命令使用后台执行。

### 16.1 适合的例子：测试与阅读文档

```text
后台：运行注册测试。

主流程：阅读README，检查说明是否清楚。
```

阅读文档不需要先知道测试结果，也不会因此改动被测代码，通常比较合适。

### 16.2 不合适的顺序：安装没结束就使用依赖

```text
后台：安装测试依赖。

主流程：立刻运行需要这些依赖的测试。
```

依赖还没安装完成，测试可能失败。这两件事存在先后关系，不能仅因为第一件慢就忽略等待。

### 16.3 要留意的例子：测试期间修改同一批代码

```text
后台：运行测试。

主流程：继续修改同一批正在被测试的文件。
```

测试期间代码状态发生变化，最后的结果可能难以解释，不能简单认为它验证了最终文件版本。

### 16.4 当前没有依赖调度器替模型判断

当前 s11 没有接入 s10 的任务依赖图。

```text
run_in_background=true：选择执行方式。

后续工作是否独立：仍要由模型根据任务判断。
```

也没有额外实现“收到后台结果后自动重试”“自动启动下游任务”等调度策略。

## 17. 输出怎样收集，长日志会怎样

### 17.1 当前不流式推送日志

执行函数使用：

```python
stdout, stderr = process.communicate(timeout=120)
```

主要在命令结束后处理收集到的输出，不会把每一行日志实时交给模型。

结果文字使用标准输出和标准错误的拼接：

```python
output = (stdout + stderr).strip()
```

因此这份文字也不保证还原 stdout 与 stderr 原本交错发生的精确顺序。

### 17.2 两层截取限制

| 阶段 | 当前限制 | 意思 |
| --- | --- | --- |
| 命令执行返回 | 最多前50,000字符 | 先限制交回给管理器的主要输出文字 |
| 生成通知 | 结果文字的前500字符 | 模型通过通知直接看到的只是前一部分 |

非零退出码等格式提示还会占用结果文字中的位置，所以不能把通知简单理解为“原始日志的完整前500字符”。

### 17.3 完整日志不会自动保存到文件

当前 `results` 在内存里，收集后移除；代码没有自动把整份后台输出写到结果文件。

如果后续需要详细排查，可以让命令把日志写进文件，再用工具读取或搜索。

例如，在当前 Unix Shell 环境中，可以把命令设计成：

```bash
pytest -q > test-output.txt 2>&1
```

再通过 `read_file` 或搜索命令查看日志。这个示例说明日志保存思路，笔记本身不会执行它。

### 17.4 结果柜不是长期归档

```text
results：临时保存待领取的结果。

messages：已经交给模型的通知历史。

磁盘日志文件：需要时由具体命令或额外逻辑负责保存。
```

不要把它们混成同一个存储。

## 18. 主程序退出以后，后台还会一直跑吗

### 18.1 后台状态在内存里

```text
BACKGROUND.tasks
BACKGROUND.results
BACKGROUND._ready
```

没有像 s10 一样保存成 `.tasks/*.json`，所以重启后不能仅靠这个管理器恢复旧命令的状态与通知。

### 18.2 daemon线程的作用

```python
daemon=True
```

可以先理解为：主程序退出时，不会为了这些线程无限等待。

但线程和 Shell 进程是两层，代码还另外跟踪 Shell 进程，并处理清理。

### 18.3 哪些路径会尝试清理命令进程

```text
命令正常结束：finally中执行清理。

命令超时：返回超时结果，同时finally中清理。

主程序正常退出：atexit回调尝试清理仍跟踪着的进程。

收到SIGTERM：信号处理函数先尝试清理，再退出。
```

Unix环境中使用独立session与进程组，尝试停止原Shell及其相关子进程；Windows分支回退到停止、强杀Shell进程，不能由此保证所有子进程都被同样处理。

清理是进程生命周期管理，不是沙箱，也不覆盖强制终止、进程逃离原进程组等所有情况。

### 18.4 本轮结束与整个程序退出不同

| 情况 | 后台命令可能怎样 |
| --- | --- |
| Agent Loop本轮返回，CLI仍在等下一次输入 | Python进程还在，后台命令可能继续跑 |
| 用户输入q，Python经正常退出路径结束 | 会尝试清理仍在运行的命令 |
| 程序退出后重新启动 | 内存登记表重新开始，旧通知没有持久恢复流程 |

这份实现展示的是“当前进程里先启动、后收集”，不是一个长期托管任务的服务。

## 19. 两个阅读源码时容易误解的位置

### 19.1 run_bash接受参数，但它自己不负责启动后台线程

```python
def run_bash(command: str, run_in_background: bool = False) -> str:
    return _format_bash_result(*_run_bash_process(command))
```

这个函数直接执行命令并等待返回。

真正的分流在外面：

```text
execute_tool
    ├─ 显式后台请求 → BackgroundManager.start
    └─ 普通执行 → call_tool → run_bash
```

因此，在 Python 中直接调用：

```python
run_bash("pytest -q", run_in_background=True)
```

不会仅凭这个参数自动启动后台线程。要沿着模型工具的统一执行入口看完整路线。

### 19.2 锁保护登记信息，不保护整个工作区

主线程收集结果，后台线程写入结果，两边都会访问：

```text
tasks
results
_ready
```

`threading.Lock()` 可以理解为：改动这本登记册前，先拿到钥匙。

例如，后台在同一个锁范围里更新状态、保存结果、加入待领取名单，主线程也在锁范围里取走完成项。

但等待整个命令结束的工作没有一直占着这把锁，否则主线程就难以继续访问管理器。

这把锁不会自动锁住测试代码或其他项目文件，也不能解决两个后台命令同时修改同一文件的问题。

### 19.3 全局别名指向同一批记录

源码中：

```python
background_tasks = BACKGROUND.tasks
background_results = BACKGROUND.results
```

它们指向管理器里的同一个字典，不是每次复制出来的独立快照。

因此收集结果时从管理器字典中移除记录，这些别名观察到的内容也会变化。

## 20. 把一次完整流程连起来看

### 20.1 用户发起任务

```text
用户：运行注册测试，等待期间检查README。
```

### 20.2 模型请求后台执行

```text
bash：pytest -q，run_in_background=true。
```

权限检查通过后：

```text
登记bg_0001。
启动后台线程。
返回“bg_0001已启动”。
```

### 20.3 主流程继续工作

```text
启动回执作为tool_result加入messages。
    ↓
再次请求模型。
    ↓
模型要求读取README。
    ↓
程序读取，返回文件内容。
```

### 20.4 后台命令在之后结束

```text
tasks[bg_0001].status = completed。
results[bg_0001] = 测试输出。
_ready加入bg_0001。
```

这一步可能和前面的模型调用、文件读取发生交错，不能假设一定刚好在读取README后完成。

### 20.5 下一次来到循环顶部

```text
collect取走完成项。
    ↓
生成task_notification。
    ↓
inject保留原消息，再追加通知文本。
    ↓
调用模型，模型看到文件内容和测试结果。
```

### 20.6 模型继续决定下一步

```text
测试成功：结合README检查结果，继续后续工作或回复用户。

测试失败：读取失败信息，检查代码，再安排修复和验证。
```

最值得跟踪的结果路线是：

```text
后台命令运行
    ↓
tasks更新状态
results保存结果
_ready登记可领取项
    ↓
collect消费完成项，生成通知
    ↓
inject把通知加入messages
    ↓
下一次主模型调用真正看到结果
```

## 21. 和前面几节放在一起理解

| 能力 | 主要解决什么 | 存储或传递位置 |
| --- | --- | --- |
| 当前对话记录 | 模型正在做什么、刚收到什么结果 | `messages` |
| s08上下文压缩 | 工作记录过长时怎样腾空间 | 结果文件、归档、摘要等 |
| s09记忆 | 以后仍然适用的知识怎样保留和召回 | `.memory/` |
| s10任务系统 | 哪项工作做到哪里，谁负责，前置任务是什么 | `.tasks/*.json` |
| s11后台执行 | 慢命令运行时主流程怎样继续，结果怎样稍后交回 | 线程、进程、内存登记表、通知 |

当前 `s11_background_tasks/code.py` 保留基础工具和Hook，增加bash后台参数与后台管理器。

它没有自动接入s08压缩、s09记忆或s10依赖任务系统。

本节工具仍是五个：

```text
bash
read_file
write_file
edit_file
glob
```

没有新增一个独立的 `check_background`、`wait_background` 或取消任务工具。完成结果主要由循环顶部的注入函数传回。

## 22. 工具、函数与参数速查

### 22.1 主要函数

| 位置 | 通俗理解 | 重点观察 |
| --- | --- | --- |
| `should_run_background` | 选择后台路径 | 必须是bash且参数明确为True |
| `execute_tool` | 工具统一入口 | 先检查权限，再同步或后台分流 |
| `BackgroundManager.start` | 登记并启动 | 分配编号、running记录、启动线程、返回编号 |
| `BackgroundManager._run` | 等命令结束并保存 | 输出格式、成功失败状态、results与_ready |
| `BackgroundManager.collect` | 领取完成项 | 移除内部记录、生成通知、防止重复领取 |
| `start_background_task` | 启动的薄包装 | 调用BACKGROUND.start |
| `collect_background_results` | 收集的薄包装 | 调用BACKGROUND.collect |
| `inject_background_results` | 把通知放到模型面前 | 保留原消息内容，追加text块 |
| `_run_bash_process` | 实际执行命令 | Popen、收集输出、120秒超时、finally清理 |
| `_format_bash_result` | 整理结果文字 | 非零退出码增加错误提示 |
| `agent_loop` | 继续模型与工具循环 | 每次模型调用前先注入通知 |

### 22.2 状态与返回内容

| 阶段 | 内部状态 | 主流程或模型收到什么 |
| --- | --- | --- |
| 刚启动且仍运行 | running | “后台已启动”的tool_result |
| 命令退出码0 | completed，结果待领取 | 此时未必已经进入消息 |
| 非零退出码、超时或worker异常 | failed，结果待领取 | 此时未必已经进入消息 |
| 主流程收集 | 完成项从管理器移除 | 返回task_notification字符串 |
| 注入后请求模型 | 通知保留在messages中 | 模型真正看到完成结果 |

### 22.3 关键参数和限制

| 参数或规则 | 当前行为 |
| --- | --- |
| `run_in_background` | 默认不进入后台，必须明确请求 |
| 后台工具范围 | 仅bash |
| 后台编号 | 当前进程内递增，类似bg_0001 |
| 后台线程 | `daemon=True` |
| 命令等待超时 | 120秒 |
| 命令返回输出 | 最多前50,000字符 |
| 通知summary | 结果文字前500字符 |
| 结果收集时间 | 之后再次进入循环、请求模型之前 |
| 完成后的自动唤醒 | 没有 |
| 记忆或任务状态持久化 | 本节后台管理器没有实现 |
| 自动重试和下游调度 | 没有 |

## 23. 复习问答

### 问题1：后台执行会让测试本身一定更快吗？

不会保证命令本身更快。它把等待交给后台，让主流程可以利用这段时间继续做独立工作。

### 问题2：命令名里有install或test，会自动放后台吗？

不会。必须是bash工具，并明确设置布尔值 `run_in_background=true`。

### 问题3：拿到“bg_0001 started”，可以说测试通过了吗？

不可以。它只是启动回执，最终可能成功、失败或超时。

### 问题4：后台线程是不是另一个模型Agent？

不是。它执行命令、等待结束、保存结果，不会自己调用模型规划后续工作。

### 问题5：为什么有tasks、results、_ready三个容器？

tasks记录命令身份和状态，results保存结果文字，_ready标记哪些完成结果可以被领取。

### 问题6：后台已经completed，模型就一定看到了吗？

不一定。结果还可能只在内存里。要等主流程收集、注入messages，再请求模型，模型才会看到。

### 问题7：最终结果为什么不再发一次相同tool_use_id的tool_result？

原工具调用已经通过启动回执回应过。后来用普通text通知，避免同一次调用出现第二份工具结果。

### 问题8：完成通知会覆盖刚读取的文件内容吗？

不会。末尾是user列表内容时追加text块；末尾是user字符串时把原文字保留为text块，再加入通知。

### 问题9：collect以后还能再次领取同一个结果吗？

不能按正常流程重复领取。它会移除已完成项和结果，清空对应待领取名单。要使用这次返回的通知。

### 问题10：只通知一次，为什么后面模型还可能看到这段文字？

不重复追加事件，不等于删除历史。通知已经保留在messages里，后续请求仍可能带上它。

### 问题11：模型已经结束本轮回答，测试之后才完成，会主动继续回答吗？

当前不会。CLI可能仍在等待输入，结果留在队列。下一次用户输入、重新进入循环时才有机会收集。

### 问题12：测试在模型正在回复时完成，会插入那次请求吗？

不会。需要以后再次来到循环顶部才能收集，不能直接修改已经发出的那次模型请求。

### 问题13：后台命令超过120秒，还会一直跑吗？

当前命令执行函数仍有120秒超时，超时返回错误，后台状态为failed，并尝试清理命令进程。

### 问题14：退出整段Python程序后，bg_0001还能重启恢复吗？

当前后台状态在内存里，程序还会尝试清理Shell进程，没有实现持久恢复和退出后的托管服务。

### 问题15：Agent Loop本轮结束，和整个程序退出一样吗？

不一样。本轮结束后CLI可能继续等待输入，Python进程和后台命令仍可能运行；整个程序退出才走退出清理。

### 问题16：通知只显示500字符，完整日志会自动存文件吗？

不会。需要完整日志时，应让具体命令或额外逻辑保存文件，再读取或搜索。

### 问题17：把依赖安装放后台，然后立刻运行依赖它的测试，合理吗？

不合理的风险很直接：依赖可能还没安装好。后续工作需要独立，或明确等前置命令结果。

### 问题18：run_bash(..., run_in_background=True)直接调用会开线程吗？

不会。分流在execute_tool中，run_bash本身仍直接执行并等待命令返回。

### 问题19：内部有Lock，是不是所有项目文件都不会发生并发冲突？

不是。锁主要保护tasks、results、_ready等内部记录，不会自动锁住工作区文件或分析命令依赖。

### 问题20：先启动bg_0001，是否一定先收到它的通知？

不一定。独立命令可能后启动的先结束，要用通知里的后台ID和command对应结果。

### 问题21：后台执行会绕过权限检查吗？

不会。PreToolUse在后台分流前执行，拒绝后不会启动后台任务。

### 问题22：本节会自动加载s10的任务依赖图吗？

没有。s11单独展示后台命令机制，未接入前一节完整的持久任务系统。

## 24. 回到源码时的阅读顺序

建议先沿着最短路线读：

```text
工具明确请求后台
    ↓
execute_tool检查权限并分流
    ↓
start登记并启动线程
    ↓
启动回执进入messages
    ↓
_run等待命令结束，写结果和_ready
    ↓
collect取走结果，生成通知
    ↓
inject追加到messages
    ↓
下一次模型调用看到结果
```

对应查找顺序：

1. `should_run_background()`：明确什么情况走后台。
2. `execute_tool()`：看权限检查、后台分流和启动回执。
3. `BackgroundManager.start()`：看编号、登记表和线程。
4. `BackgroundManager._run()`：看完成、失败和待领取名单。
5. `BackgroundManager.collect()`：看结果清理和通知格式。
6. `inject_background_results()`：看原消息与通知怎样放到一起。
7. `agent_loop()`：看注入发生在每次主模型调用之前。
8. `_run_bash_process()` 和清理函数：最后再看实际命令、超时和进程生命周期。

先跟踪 `tasks → results → _ready → messages` 这条结果传递路线，再研究跨平台分支、进程组和异常细节。
