# s12 Cron Scheduler：按时间给 Agent 派发任务

s12 保存一条时间规则和一条任务描述。时间匹配时，程序先把请求放进队列，等 Agent 有空再交给模型。我们用同一个例子走一遍 **“每天 09:00 运行注册测试，并汇总结果”**。

复习时可以先看时间线，再按问题跳到对应章节。示例中的日期、任务 ID 和模型回复都是演示数据。源码与课程说明见 [code.py](code.py) 和 [中文 README](README.zh.md)。

## 1. 从 s11 到 s12

| 用户需求 | 对应章节 | 程序做什么 |
| --- | --- | --- |
| 现在启动测试，等待时先读 README | s11 Background Tasks | 启动后台命令，先返回编号，之后收集命令结果 |
| 每天 09:00 开始检查测试 | s12 Cron Scheduler | 保存时间规则，到期后把任务描述交给模型 |

以每天跑测试为例，整个过程有三个不同的时刻。

| 时刻 | 发生了什么 | 测试进行到哪一步 |
| --- | --- | --- |
| 到期 | 当前时间匹配规则，请求进入队列 | 还在排队 |
| 确认交付 | 包含定时请求的模型调用已经收到响应 | 模型可能刚提出要调用 `bash` |
| 实际完成 | 测试命令执行并返回结果，Agent 处理结果 | 可以根据输出判断通过或失败 |

所以你看到日志里的 `[cron] due` 时，可以先读成“任务到期并已入队”。看到 `[cron] delivered` 时，请求刚被追加到 `messages`，接下来的模型调用仍可能失败。代码在模型返回后才执行确认。

## 2. 读懂五段式 Cron

每个表达式由五段组成，按以下顺序读取。

```text
分钟   小时   每月几号   月份   星期几
 0      9        *        *       *
```

`0 9 * * *` 要求小时为 9、分钟为 0。后三个 `*` 对日期、月份和星期都放行，所以每天 09:00 这一分钟匹配。

| 表达式 | 什么时候匹配 |
| --- | --- |
| `* * * * *` | 每一分钟 |
| `0 9 * * *` | 每天 09:00 |
| `30 18 * * *` | 每天 18:30 |
| `*/5 * * * *` | 每小时的第 00、05、10、15……55 分钟 |
| `0 9 * * 1-5` | 周一到周五的 09:00 |
| `0 9,18 * * *` | 每天 09:00 和 18:00 |

单个字段支持 `*`、`*/N`、指定数字、范围 `N-M` 和逗号列表。星期使用 `0` 表示周日、`1` 表示周一，直到 `6` 表示周六。代码用 `(moment.weekday() + 1) % 7` 把 Python 的星期值转换成这个顺序。

### 09:03 创建每 5 分钟的任务

假设 09:03 注册 `*/5 * * * *`。源码判断的是 `moment.minute % 5 == 0`。

| 检查时刻 | 分钟字段 | 是否匹配 |
| --- | --- | --- |
| 09:03 | `3 % 5 == 3` | 否 |
| 09:05 | `5 % 5 == 0` | 是 |
| 09:08 | `8 % 5 == 3` | 否 |
| 09:10 | `10 % 5 == 0` | 是 |

这条规则始终对准时钟上的分钟刻度。在 09:03 创建，下一次通常是 09:05。如果创建时已经处在 09:05 这一分钟，后续轮询也可能在当前分钟触发。

### 每月几号和星期几同时填写

以 `0 9 1 * 1` 为例，分钟、小时和月份先通过判断。因为日期和星期都写了限制，源码接着用 `day_matches or weekday_matches`。

| 当前时刻 | 每月几号匹配 | 星期匹配 | 会触发吗 |
| --- | --- | --- | --- |
| 2026-11-01 09:00，周日 | 是 | 否 | 会 |
| 2026-11-16 09:00，周一 | 否 | 是 | 会 |
| 2026-11-17 09:00，周二 | 否 | 否 | 不会 |

因此这条规则会匹配每月 1 号和每周一的 09:00。如果日期和星期只有一项受限，就按那一项判断。如果两者都是 `*`，这两个字段都放行。

### 输入校验

| 字段 | 允许的数字范围 |
| --- | --- |
| 分钟 | `0–59` |
| 小时 | `0–23` |
| 每月几号 | `1–31` |
| 月份 | `1–12` |
| 星期几 | `0–6` |

`validate_cron()` 会在创建前检查字段数量和取值。`0 24 * * *` 因为小时越界被拒绝，`0 9 * *` 因为缺字段被拒绝，`*/0 * * * *` 因为步长必须为正数被拒绝。字段通过检查只代表格式和取值符合要求。例如 `0 9 31 2 *` 各字段均在范围内，实际日期中却没有 2 月 31 日可以匹配。

调度线程用 `datetime.now()` 取运行环境的本地时间。每条规则没有单独的时区字段。本文的钟点都按示例进程的本地时间理解。

## 3. 创建规则和保存文件

假设 08:59 用户说“每天 09:00 运行注册测试，并汇总结果”。模型可以发出这样的工具请求。

```json
{
  "name": "schedule_cron",
  "input": {
    "cron": "0 9 * * *",
    "prompt": "运行注册测试，并汇总结果。",
    "recurring": true,
    "durable": true
  }
}
```

`schedule_job()` 校验 Cron 和提示词，分配一个 `cron_` 加八位十六进制字符的 ID，再把 `CronJob` 放入 `scheduled_jobs`。空白提示词会被拒绝。下面假设分配到 `cron_a1b2c3d4`。

```text
操作前
scheduled_jobs = {}
cron_queue = []

操作后
scheduled_jobs 包含 cron_a1b2c3d4
cron_queue = []
```

因为示例使用 `durable=true`，当前工作目录下的 `.scheduled_tasks.json` 还会保存一份记录。文件最外层是列表。

```json
[
  {
    "id": "cron_a1b2c3d4",
    "cron": "0 9 * * *",
    "prompt": "运行注册测试，并汇总结果。",
    "recurring": true,
    "durable": true,
    "pending_delivery": false,
    "last_fired": null
  }
]
```

| 字段 | 可以怎样读 |
| --- | --- |
| `id` | 用来识别和取消这条规则 |
| `cron` | 哪些本地时间会匹配 |
| `prompt` | 到期后交给模型的任务描述 |
| `recurring` | 确认交付后是否保留规则，供以后再次触发 |
| `durable` | 是否保存到文件，供重启后加载 |
| `pending_delivery` | 是否还有一份已经触发、尚待确认的交付 |
| `last_fired` | 上次触发的日期和分钟，用于同一分钟去重 |

`recurring` 和 `durable` 默认都为 `true`，可以独立选择。

| `recurring` | `durable` | 示例 |
| --- | --- | --- |
| `true` | `true` | 持续每天 09:00 跑测试，规则跨重启保留 |
| `true` | `false` | 本次程序运行期间，每 5 分钟检查一次报告 |
| `false` | `true` | 下一次匹配时提醒检查报告，规则可以先保存过夜 |
| `false` | `false` | 当前进程中下一次匹配时提醒一次 |

例如“一次性、下一次 10:00 提醒”可以用 `0 10 * * *` 和 `recurring=false`。Cron 仍按小时和分钟匹配，成功确认一次交付后就删除规则。这种写法也会匹配创建时所在的 10:00 分钟。

保存时，`save_durable_jobs()` 只收集需要持久化的记录，先把新列表写进临时文件，再用 `os.replace()` 替换正式文件。如果创建规则时保存失败，`schedule_job()` 会把刚加入的内存记录移除。重启时要从同一工作目录加载同一个 `.scheduled_tasks.json`。

## 4. 到期入队与同一分钟去重

`cron_scheduler_loop()` 大约每秒调用一次 `poll_due_jobs(datetime.now())`。以刚才的规则为例。

| 检查时刻 | 程序判断 | `pending_delivery` | `last_fired` | `cron_queue` |
| --- | --- | --- | --- | --- |
| 08:59:59 | 小时或分钟不匹配 | `false` | `null` | `[]` |
| 09:00:01 | 匹配，第一次排队 | `true` | `2026-11-16 09:00` | `[cron_a1b2c3d4]` |
| 09:00:02 | 上一份还在等交付 | `true` | `2026-11-16 09:00` | 仍只有一份 |

表格最后一列用 ID 简写，实际队列里存放的是 `CronJob` 对象。进入队列只表示这份请求可以交给 Agent，真正执行测试还在后面。

`_enqueue_due_job()` 会先更新 `pending_delivery` 和 `last_fired`。持久任务还会先保存这些字段，再追加到内存队列。如果文件写入失败，它把两个字段恢复成旧值，这次不会入队。之后的轮询如果还在匹配分钟内，可以重新尝试。

`poll_due_jobs()` 有两道跳过条件。

- `pending_delivery=True` 表示已有一份请求等待确认。这件事还挂着时，经过更多匹配分钟也不会继续积压同一规则的新请求。
- `last_fired == minute_marker` 表示当前分钟已经触发过。即使任务在 09:00:10 就确认交付，09:00:11 再检查也会跳过。

例如每分钟一次的规则在 09:00 入队，但 Agent 一直忙到 09:03，期间队列里仍然只有此前那一份请求。时间匹配精度是分钟，实际开始时刻还受轮询和 Agent 忙碌情况影响。

## 5. Agent 忙碌与空闲时的行为

s12 的 CLI 有三条执行路线。

| 执行路线 | 工作内容 |
| --- | --- |
| 主线程 | 等终端输入，收到问题后持有 `agent_lock` 运行用户回合 |
| 调度线程 | 大约每秒看钟，找出到期规则并入队 |
| 队列处理线程 | 大约每 0.2 秒检查队列，尝试取得 `agent_lock` 并启动定时回合 |

`cron_lock` 保护调度登记表、队列以及相关保存动作。`agent_lock` 控制谁可以运行 Agent 回合，串行使用共享的 `session_history`。

### 到点时 Agent 正在处理用户问题

```text
08:59  用户问“检查一下注册代码”，用户回合拿到 agent_lock。
09:00  调度线程发现测试规则到期，正常入队。
09:01  队列线程尝试拿锁，用户回合仍在运行，于是稍后再检查。
09:03  用户回合结束，释放锁。
随后   队列线程拿到锁，启动一次 Agent 回合来处理待交付请求。
```

队列处理线程用 `agent_lock.acquire(blocking=False)` 尝试拿锁。拿不到就留待下次检查。调度线程仍然可以继续看钟，因为入队使用的是另一把锁。

### 终端只是在等下一次输入

主线程等待 `s12 >>` 的输入时，还没有占用 `agent_lock`。只要队列有活，队列线程就可以取得锁并调用 `run_agent_turn_locked()`，用户无需补一句“继续”。这就是本节能在程序空闲时主动开始处理的原因。

## 6. 把请求交给模型

`agent_loop()` 入口调用 `consume_cron_queue()`，把当前队列复制出来并清空队列。当时取到的每条任务都会变成一条带 `[Scheduled]` 前缀的 `user` 消息。

处理前，例如历史里已有这两条消息。

```json
[
  {"role": "user", "content": "帮我检查注册代码。"},
  {"role": "assistant", "content": "已经检查完了。"}
]
```

将到期请求取出后，准备发给模型的历史变成下面这样。

```json
[
  {"role": "user", "content": "帮我检查注册代码。"},
  {"role": "assistant", "content": "已经检查完了。"},
  {"role": "user", "content": "[Scheduled] 运行注册测试，并汇总结果。"}
]
```

模型收到任务描述后，可以提出 `bash` 工具调用来执行 `pytest -q`。程序执行工具后，再把测试输出作为对应的 `tool_result` 交回模型。`[Scheduled]` 是请求内容的文本前缀。

队列在每次进入 `agent_loop()` 时取一次。已经进入循环的回合随后发起多次模型调用，也不会每次重新取定时队列。新的到期请求会等后续回合处理。

如果队列起初有多条任务，代码会把它们一起追加到同一轮的历史。如果用户输入先拿到锁，而队列中正好有定时请求，这次用户回合也可能顺带取走它们。普通请求与定时请求使用同一份会话历史。

## 7. 交付确认与失败重试

### 模型成功返回，周期任务继续保留

程序收到本轮首次模型响应后，先执行 `acknowledge_cron_jobs()`，随后才运行模型提出的工具调用。假设首次响应只提出“调用 `bash` 运行 `pytest -q`”，在命令真正执行前，周期规则已经变成如下状态。

```text
交付前
pending_delivery = true
last_fired = "2026-11-16 09:00"

确认后
pending_delivery = false
last_fired = "2026-11-16 09:00"
```

规则仍在登记表里。同一分钟由 `last_fired` 去重，下一个匹配时间可以再次到期。`pending_delivery=false` 表示这份请求无需继续等待交付，测试结果要到工具执行后才知道。

### 模型成功返回，一次性规则会删除

假设规则为 `0 10 * * *`、`recurring=false`，内容是“提醒检查测试报告”。10:00 到期以后，它与周期任务使用同样的排队流程。收到模型响应后，`acknowledge_cron_jobs()` 把该规则从 `scheduled_jobs` 移除，持久任务还会更新文件。

如果一次性请求是“运行测试”，而之后测试失败，这份调度规则已经消耗掉。处理测试失败属于后续 Agent 工作。

### 首次模型调用失败，撤回消息并把请求放回队列

假设网络在交付时出错。`scheduled_start` 记住追加定时消息前的历史长度，`waiting_for_ack` 记住这批尚待确认的任务。

```text
请求模型前
messages   = [原来的对话, "[Scheduled] 运行注册测试，并汇总结果。"]
cron_queue = []
pending_delivery = true

首次调用失败后
messages   = [原来的对话]
cron_queue = [cron_a1b2c3d4]
pending_delivery = true
```

队列线程之后可以再次尝试。正常的失败回退会删掉这次刚加的消息，所以连续失败时，历史里不会为每次尝试留一条相同的 `[Scheduled]`。

如果首次调用已经成功并确认了交付，而后续工具执行或模型调用失败，代码不会走这条首次交付的回退路径。

### 模型返回了，但保存确认状态失败

另一种失败点出现在 `acknowledge_cron_jobs()`。模型已返回，但写入持久任务文件时出错。代码会恢复内存中的待交付状态和被删除的一次性规则，并将相关任务放回队列。当前回合保留这次已追加的定时消息和模型响应，之后仍可继续处理工具调用，队列中的请求也可能再次交付。这与首次模型调用失败时撤回消息的处理不同。

## 8. 重启后恢复什么

### 停机期间经过了一个匹配时刻

```text
08:50  退出程序。文件里有每天 09:00 的规则，pending_delivery=false。
09:00  程序没有运行，这次匹配没有被观察到。
10:00  重启，加载规则。当前 10:00 与规则不匹配。
次日   程序仍在运行的话，下一次 09:00 可以正常入队。
```

轮询检查的是当前时刻，因此重启时不会逐个补跑停机时错过的时间点。

### 停机前已入队，但还没确认交付

```text
09:00  规则已经触发。文件里保存了 pending_delivery=true。
09:01  确认交付前，程序退出。
10:00  重启时加载记录，发现仍待交付，重新加入 cron_queue。
```

这里恢复的是一份之前已记录的请求，即使 10:00 已经超出原先的匹配分钟，也可以继续交付。只在内存中登记的 `durable=false` 任务会随进程退出消失。

### 为什么恢复后可能再次交付

假如模型已经成功返回，但程序在确认状态写回磁盘之前退出，磁盘仍可能保留 `pending_delivery=true`。下一次启动会再次提交这份请求。这种设计优先恢复尚未确认的交付，所以允许重复提交。`last_fired` 防的是轮询时同一分钟的再次触发，恢复队列则依据文件里保存的待交付状态。

`load_durable_jobs()` 遇到无法解析的持久文件时会输出日志。文件外层有效而个别记录未通过校验时，代码会报告并跳过相应记录。

## 9. 查看和取消规则

| 工具 | 用途 |
| --- | --- |
| `schedule_cron` | 创建一条规则，返回生成的 ID |
| `list_crons` | 查看已登记的规则、概要和模式 |
| `cancel_cron` | 根据 ID 移除规则和队列中的相应待交付项 |

列表中的一行大致如下。

```text
cron_a1b2c3d4: 0 9 * * * -> 运行注册测试，并汇总结果。 [recurring, durable]
```

如果要取消它，工具参数使用创建时返回的真实 ID。

```json
{
  "name": "cancel_cron",
  "input": {"job_id": "cron_a1b2c3d4"}
}
```

假设取消时任务已经到期但还在内存队列里。取消前，登记表、队列和持久文件里都有对应信息。取消后，登记表移除规则，队列过滤这个 ID，持久文件重新保存。保存失败时会恢复原登记和队列。如果 `pytest` 已启动，取消规则没有操作该进程的逻辑，命令会按原来的工具执行流程处理。

## 10. 权限与运行边界

- 定时回合里的工具仍经过 `PreToolUse`。队列线程遇到需要交互批准的操作时，`request_permission()` 直接返回 `Permission denied: scheduled turns cannot request interactive approval`，不会和主终端同时读输入。判断依据是当前线程，具体工具调用仍由权限 Hook 处理。
- 运行 CLI 时，`start_runtime_threads()` 先加载持久记录，再启动调度线程和队列处理线程。单纯导入模块时，这两个线程保持未启动。CLI 正常退出时会设置停止事件，并对每个线程尝试等待至多一秒。
- 当前 s12 的 `bash` 仍然同步等待命令结果，有 120 秒的超时设置。调度线程可以继续把其他到期请求加入队列，当前 Agent 回合占用 `agent_lock` 时，其他定时回合继续排队。这份文件的工具由五个基础工具和三个定时工具组成。

## 12. 复习问答

**1. 09:03 注册 `*/5 * * * *`，下一次匹配几点？** 09:05。它用时钟上的分钟值做判断。

**2. 每秒检查一次，为什么 09:00 通常只排一份？** 交付前有 `pending_delivery` 防止多排，交付后同一分钟仍受 `last_fired` 限制。

**3. 到点时用户回合正在修改代码，定时请求放在哪里？** 放在 `cron_queue`，等有回合取得 `agent_lock` 后再取走。

**4. 终端在等用户输入，到期任务还需要用户发消息吗？** 不需要。队列处理线程可以拿锁并启动 Agent 回合。

**5. 一次性测试任务什么时候删除？** 模型为包含定时请求的首次调用返回响应后，调度器就尝试确认并删除规则。测试可能还没运行。

**6. 第一次模型调用报错，为什么历史里不会多一条同样的请求？** 程序把这次追加的定时消息撤回，并把任务重新排队。

**7. 08:50 关掉程序，10:00 重启，会补跑 09:00 吗？** 如果程序关闭前还没记录到期，则不会补跑。如果已经保存为待交付，重启会恢复那份请求。

**8. 取消规则后，已经启动的测试会结束吗？** 取消处理的是规则和仍在排队的请求，已启动的命令由原来的执行流程继续处理。

**9. `0 9 1 * 1` 只在每月 1 号恰好为周一时触发吗？** 源码对这两个受限日期字段取“或”，所以任意一个满足即可。
