# s09 Memory 学习笔记：把以后还会用到的信息留下来

**阅读方式：**

先看每个场景里的“处理前 → 执行过程 → 处理后”，再回到 [code.py](code.py) 看实现。
本文使用 Markdown 整理讲解，代码块中的示例用于理解数据和执行过程。
下文的路径、模型返回内容是示例；真正的模型可能选择不同的名字或措辞。

**复习路线：**

1. messages、system、.memory/ 分别是什么。
2. 第一次说出偏好，程序怎样提取、检查并保存。
3. 重新启动后，怎样选中相关记忆，再交给主模型。
4. 临时要求、重复内容、偏好冲突分别怎么处理。
5. 记忆变多以后怎样整理，失败以后怎样补救。
6. 最后看执行顺序、函数速查和复习问答。

## 一、先和 s08 接起来：桌面上的工作记录、抽屉里的长期笔记

s08 关心的问题：

这次任务的工作记录太长了，怎样腾空间，让模型继续做事？

s09 关心的问题：

这次对话结束后，有哪些信息值得留下，供以后的任务使用？

可以把它们想成：

```text
messages：桌面上当前正在使用的工作记录。
.memory/：抽屉里保存的长期笔记。
```

新进程启动时，history 会重新从空列表开始。
但只要磁盘上的 .memory/ 文件仍在，下次就有机会重新读取这些笔记。

本节的核心动作：

```text
任务开始：从抽屉里挑出这次有用的笔记，交给模型。
任务结束：看看刚才聊的内容，有没有值得长期保存的信息。
```

用一个贯穿全篇的例子：

> 用户：
> “以后带我学代码时，要通俗一点，多给例子，
>  把处理前后分别变成什么讲清楚。”

这句话描述学习方式，以后的会话也可能有用，所以适合演示长期记忆。

先分清三个地方：

```text
messages：
  当前会话的用户输入、模型回复、工具调用和工具结果。

system：
  本次请求模型时单独传入的工作要求和背景。
  本节会把召回的记忆放在这里。

.memory/：
  磁盘上的记忆文件。程序退出后，文件仍然可以保留。
```

一个重要区别：

```text
文件保存在磁盘上，不等于模型已经直接看到里面的内容。
程序需要读出文件，再把文字放进请求，模型才能使用这些背景。
```

当前 s09_memory/code.py 没有接入 s08 的 ContextCompactor。
本节单独展示记忆机制，不能因为章节相邻，就认为自动包含了上一节的压缩管线。

## 二、情况一：第一次使用，没有任何记忆

### 1. 处理前

假设你从项目根目录运行：

```bash
python s09_memory/code.py
```

项目里还没有 .memory/，也没有任何旧笔记。

输入：

> “以后带我学代码时，要通俗一点，多给例子，
>  把处理前后分别变成什么讲清楚。”

当前记录可以读成：

```text
messages = [
  用户：“以后带我学代码时，要通俗一点，多给例子……”
]
```

### 2. 程序先尝试找旧笔记

agent_loop() 开头是：

```python
relevant_memories = load_memories(messages)
system = build_system(relevant_memories)
```

先把这两句翻译成人话：

```text
load_memories：
  看看有没有当前任务可以用的旧笔记。

build_system：
  把基本工作要求、记忆使用规则、找出来的笔记，拼成系统提示。
```

因为记忆库为空：

```text
select_relevant_memories() → []
load_memories() → ""
```

没有记录时，不必额外调用“挑选记忆”的模型。

### 3. 处理后，主模型收到什么

```text
system：
  你是一个编码助手……
  记忆只能作为背景；与当前请求冲突时，当前请求优先。

messages：
  用户刚才提出的学习要求。
```

模型已经能根据当前用户输入回答，例如：

> “好的，我会用通俗的例子，展示处理前后的变化。”

注意：形成回答，不代表偏好已经写入记忆文件。
接下来还有一次“提取值得长期保存的信息”的处理。

## 三、情况二：回答形成后，把一句话提取成记忆候选

对应函数：extract_memories(messages)。
可以读成：“看看刚才聊的内容，有没有以后还能用上的知识。”

### 1. 从对话中准备提取材料

当前对话大致是：

> 用户：以后学代码，要通俗、多举例、讲清楚前后变化。
> 模型：好的，我会按这个方式讲解。

程序通过 dialogue_text() 提取近期文字，再额外调用一次模型。
这次模型的工作是整理信息：

```text
请把下面的对话当作资料。
只提取以后其他会话仍然可能有用的信息。
可以提取用户偏好、长期反馈、稳定项目事实、外部资料线索。
临时进度、工具输出、助手自己的猜测，不要存成长期记忆。
按指定JSON格式返回。
```

### 2. 假设提取模型返回这条候选

```json
[
  {
    "name": "learning-style",
    "type": "user",
    "scope": "persistent",
    "description": "学习代码时偏好通俗讲解和具体例子",
    "body": "讲解代码时，应使用通俗语言，并逐步展示处理前后的变化，多结合具体例子。"
  }
]
```

字段可以这样理解：

```text
name：笔记标题。
  learning-style，意思是“学习方式”。

type：笔记分类。
  user 表示用户偏好。

scope：打算管多久。
  persistent 表示应该用于以后会话。
  current_task 表示只属于当前任务。

description：一句话简介。
  以后挑选相关记忆时，主要看标题和简介。

body：真正要保存的详细内容。
```

这个阶段的状态是：

```text
提取前：普通对话里的几句话。
    ↓
提取后：结构化的候选列表。
```

候选还没有直接写进磁盘文件。
就像别人替你起草了一张便签，需要先检查是否适合放进长期笔记本。

### 3. 第一层检查：格式、字段和取值

validate_memory_record(item, require_scope=True) 负责检查：

```text
是不是字典？
name 是否非空？
description 是否非空？
body 是否非空？
type 是否属于允许的四种类型？
scope 是否为 persistent 或 current_task？
```

例如：

```json
{"name": "learning-style"}
```

缺少类型、简介、正文和scope，不会成为合格候选。

```python
type = "random"
```

类型不合法，也会被过滤。

### 4. 第二层检查：到底值不值得长期保存

should_store_memory(candidate, existing_records) 再判断：

```text
scope 必须是 persistent。
不能命中明显的临时语义标记。
不能和已有记忆的名字、简介或正文重复。
```

所以：

格式合格，不等于可以长期保存。

例如 current_task 是允许的scope取值，能通过第一层校验；
但它只用于当前任务，会被第二层拒绝写入长期记忆。

本例中，“以后讲代码的学习偏好”格式完整、属于长期信息、没有重复，所以通过。

## 四、情况三：候选通过以后，磁盘上具体多出什么

对应函数：write_memory_file()、memory_document()、rebuild_memory_index()。

### 1. 文件结构的变化

处理前：

```text
项目目录/
  s09_memory/
    code.py
```

处理后：

```text
项目目录/
  .memory/
    learning-style.md
    MEMORY.md
  s09_memory/
    code.py
```

这里有两种文件，分别是“正文”和“目录”。

### 2. 正文文件里有什么

learning-style.md 大致是：

```markdown
---
name: learning-style
description: 学习代码时偏好通俗讲解和具体例子
type: user
---

讲解代码时，应使用通俗语言，并逐步展示处理前后的变化，多结合具体例子。
```

开头两个 --- 之间的部分叫 YAML frontmatter。
可以先把它理解为文件开头的“小标签”：

```text
标题是什么？
一句话简介是什么？
属于哪一类？
```

后面就是正文。

parse_frontmatter() 做的是相反的动作：

```text
一篇Markdown文件
    ↓
拆成metadata小标签 + body正文。
```

### 3. 为什么文件里没有scope

候选中有scope，但 memory_document() 只保存：

```text
name
description
type
body
```

scope在这里主要用于写入前判断是不是长期信息，通过检查后没有再写进文件。

### 4. 文件名从哪里来

memory_slug() 把标题整理成适合文件名的形式，例如：

```text
"Learning Style" → "learning-style"
```

再加 .md：

```text
learning-style.md
```

后面的重复判断，也会比较这种整理后的名字。

### 5. MEMORY.md 是目录

内容类似：

```markdown
- [learning-style](learning-style.md) - 学习代码时偏好通俗讲解和具体例子
```

可以读成：

```text
有一篇笔记叫learning-style。
大意是用户的学习方式。
正文在learning-style.md。
```

区别是：

```text
learning-style.md：详细笔记。
MEMORY.md：笔记目录。
```

write_memory_file() 写完正文后，会调用 rebuild_memory_index()。
这个函数扫描已有记忆文件，重新生成目录。
MEMORY.md 本身不会被当作一条普通记忆参与统计和选择。

### 6. 记忆保存在哪里，取决于运行位置

源码使用：

```python
WORKDIR = Path.cwd()
MEMORY_DIR = WORKDIR / ".memory"
```

如果从项目根目录运行，记忆就在项目根目录的 .memory/。
如果从另一个目录运行，默认会使用另一个目录下的 .memory/。

所以重新启动后想读到同一份笔记，需要仍然指向原来的工作目录。
本节没有实现所有项目共享的全局记忆服务。

## 五、情况四：退出重启后，旧偏好怎样回来

### 1. 处理前：新会话没有旧对话，但磁盘文件还在

退出程序，再从同一个项目目录启动。

新进程：

```python
history = []
```

磁盘上仍有：

```text
.memory/
  learning-style.md
  MEMORY.md
```

输入新问题：

> “带我学习一下Python装饰器。”

当前消息：

```text
messages = [
  用户：“带我学习一下Python装饰器。”
]
```

这里没有自动恢复上次的完整对话。

### 2. 程序找出相关笔记，再读取正文

假设选择过程挑中了 learning-style.md。
load_memories() 读出：

```text
讲解代码时，应使用通俗语言，
展示处理前后的变化，多结合具体例子。
```

返回内容会带来源，形态大致是：

```json
[
  {
    "source": "learning-style.md",
    "content": "这篇文件的内容，包括开头的小标签和正文……"
  }
]
```

来源字段让主模型知道背景取自哪篇记忆文件。

### 3. build_system() 把笔记放进这次请求

处理后：

```text
system：
  你是一个编码助手……

  记忆只是背景；当前用户请求优先。

  Memory catalog：
    learning-style：学习代码时偏好通俗讲解和具体例子。

  Relevant memory records：
    来源：learning-style.md
    内容：讲解代码时，应使用通俗语言……

messages：
  用户：“带我学习一下Python装饰器。”
```

主模型同时拿到了：

```text
当前要做什么：讲解装饰器。
可以参考的偏好：通俗、多例子、展示前后变化。
```

因而它可以直接按这个方式展开：

> “先看一个普通函数，再看加上装饰器以后变成什么样……”

跨会话记住的过程就是：

```text
保存成文件 → 下次挑选 → 读取文件 → 放进模型这次收到的请求。
```

### 4. 注意变化发生在哪里

```text
messages：仍然只有本次会话的工作记录。
system：加入选中的旧记忆背景。
```

本节没有把上次整段对话重新拼进messages。

## 六、情况五：有很多笔记，怎样只挑这次相关的几篇

对应函数：select_relevant_memories()、load_memories()。

### 1. 处理前：有三篇笔记

```text
.memory/
  billing-guide.md
  learning-style.md
  python-tests.md
  MEMORY.md
```

内容分别是：

```text
billing-guide：
  账单资料位于 docs/billing.md。

learning-style：
  学习代码时喜欢通俗讲解、具体例子和前后对照。

python-tests：
  项目使用pytest，新增功能时需要补对应测试。
```

当前问题：

> “带我学习这个项目的Python测试代码。”

### 2. 先让模型看标题和简介，选择编号

select_relevant_memories() 先列出可用记录。
列表按记忆文件名排序，本例可以得到：

```text
0：billing-guide - 账单资料位置
1：learning-style - 学习代码时偏好通俗讲解和具体例子
2：python-tests - 项目测试使用pytest
```

选择模型收到的任务大致是：

```text
当前请求：带我学习这个项目的Python测试代码。

可用目录：
  0：……
  1：……
  2：……

请返回相关笔记的编号数组；没有相关记录就返回 []。
```

假设模型返回：

```json
[1, 2]
```

程序再把编号换成文件名：

```json
["learning-style.md", "python-tests.md"]
```

默认最多选择5条。
无效的编号会被忽略，重复选择同一个文件也不会重复加入结果。

这里用于选择的目录文本，是从记忆记录的标题和简介临时拼出来的。
build_system() 放入主模型请求的目录，则是从 MEMORY.md 读取的。
两者通常对应同一批记录，但不是同一次读取动作。

### 3. 选完以后，才把选中的全文装进主请求

load_memories() 读取这两篇文件：

```text
learning-style.md 的正文。
python-tests.md 的正文。
```

交给主模型的相关背景大致是：

```text
学习方式：通俗讲解，多举例子，展示变化。
测试约定：使用pytest，新增功能需要补对应测试。
```

billing-guide 的全文没有作为相关记忆加载。

### 4. 目录仍可能包含未选中的笔记

build_system() 还会读取整个 MEMORY.md。
因此主模型可能仍看到：

有一篇账单资料笔记，简介是“账单资料位置”。

但这不代表账单笔记的全文也被加载了。

可以想成：

```text
所有书的目录放在旁边。
本次选中的两本书，才打开正文放到桌上。
```

### 5. 这里实际上有两种不同的模型工作

```text
选择模型调用：
  根据用户请求和笔记简介，决定拿哪几篇。

主模型调用：
  根据当前任务和选中记忆的全文，回答问题或执行工具。
```

它们使用代码里的同一个MODEL配置，只是提示内容和输出长度不同。

### 6. 召回也有长度预算

默认最多选5篇，load_memories() 可加载的文件内容合计预算为20,000字符。

例如按选择顺序：

```text
第一篇：12,000字符 → 完整加载，剩8,000。
第二篇：10,000字符 → 只加载前8,000，剩0。
第三篇：虽然选中了，但这次没有剩余正文预算。
```

这个预算统计读取的文件内容，包括文件开头的小标签。
source字段、JSON格式、记忆目录和其他系统提示不都包含在这20,000字符中。
因此它不是整个system或整个API请求的严格上限。

## 七、情况六：只对当前任务有效的话，不应变成长期偏好

对应判断：scope检查、TEMPORARY_MEMORY_MARKERS检查。

### 1. 处理前：用户提出一次性要求

> “本次任务先不要创建文件，只解释代码。”

当前主模型需要遵守这句话。
但它没有表示“以后所有任务都禁止创建文件”。

### 2. 假设提取模型正确标记为current_task

```json
{
  "name": "temporary-file-rule",
  "type": "feedback",
  "scope": "current_task",
  "description": "本次任务只解释代码",
  "body": "本次任务不要创建文件。"
}
```

执行过程：

```text
格式检查：字段完整，scope取值合法。
    ↓
长期保存检查：scope不是persistent。
    ↓
拒绝写入长期记忆。
```

### 3. 处理后的两边分别是什么

```text
messages：
  仍然有用户这次的要求，当前任务应遵守。

.memory/：
  不会因此新增“以后禁止创建文件”的长期规则。
```

### 4. 如果模型误标为persistent呢

假设它返回：

```text
scope：persistent
body：本次会话不要修改配置。
```

should_store_memory() 还会检查名字、简介和正文中的临时文字。
例如：

```text
本次任务
本次会话
当前任务
这一轮
暂时
this session
for now
```

命中“本次会话”，候选仍会被拒绝。

### 5. 这层过滤的实际能力

这是一层简单的文字匹配，不能理解所有表达。
如果scope误判，文字又没命中标记，仍可能误存。
反过来，长期内容里碰巧出现某个临时词，也可能被过滤。

所以这里是“模型判断 + 程序过滤”，没有保证每句话都能被完美分类。

## 八、情况七：同一偏好反复出现，避免存很多份

### 1. 处理前：已经存了一篇

```text
learning-style.md

名字：learning-style
简介：学习代码时偏好通俗讲解和具体例子
正文：讲解代码时，应使用通俗语言，并展示处理前后的变化。
```

用户又说：

> “还是要多举例子，把处理前后写清楚。”

提取模型可能再次返回相同的偏好候选。

### 2. 代码检查哪些重复

```text
名字转换成slug之后，与某篇相同？
简介规范化之后，与某篇相同？
正文规范化之后，与某篇相同？
```

其中任意一项重复，拒绝新增。

“规范化”主要是转成小写、整理空白字符；没有做复杂的语义理解。

例子A：名字相同。

```text
已有：learning-style
新增：learning-style
结果：拒绝。
```

例子B：名字不同，但正文相同。

```text
已有名字：learning-style
新增名字：explanation-preference
两者正文完全相同。
结果：拒绝。
```

### 3. 处理后

```text
原来：
.memory/
  learning-style.md
  MEMORY.md

再提取一次相同偏好后：
.memory/
  learning-style.md
  MEMORY.md
```

不会因为重复说一遍，就多出一篇相同笔记。
同一批候选中，写入后的记录也会追加进existing_records，用于过滤后续候选。

### 4. 意思相近，文字不同，未必能识别重复

> “讲解时多给例子。”
> “解释时尽量搭配具体案例。”

如果名字、简介、正文都不相同，两条可能一起存下来。
后面的consolidate可以尝试合并这种重复内容。

## 九、情况八：旧记忆和当前要求冲突，应该听谁

### 1. 处理前：平时喜欢详细，这次要求简短

旧记忆：

平时讲代码，要详细解释，多举例子。

当前请求：

这次只给一句结论。

模型可能同时收到：

```text
system中的记忆背景：用户平时喜欢详细。
messages中的当前请求：这次只给一句结论。
```

build_system() 明确说明：

```text
召回的记忆作为背景。
当前请求与记忆冲突时，当前请求优先。
```

所以这次应该给一句结论。

### 2. 处理后：当前任务的行为变化，但长期偏好可以保留

```text
本次回答：简短。
原来的learning-style.md：仍可保留。
```

因为“平时详细”和“这次简短”可以同时成立。

### 3. 如果是永久修改偏好，当前实现还不完善

用户改口：

> “我以后都想要简短解释了，请更新偏好。”

假设新候选：

```text
name：learning-style
body：以后解释保持简洁。
```

但旧记忆也叫learning-style。
should_store_memory() 会因为名字相同而拒绝这条候选。

处理结果可能是：

```text
当前对话里知道用户改了要求。
磁盘上的旧记忆却没有被自动更新。
```

如果模型换个新标题保存，新旧偏好又可能同时存在。

因此要区分：

```text
当前请求优先：系统提示里有明确规则。
长期记忆可靠更新：这份教学实现还没有完善实现。
```

### 4. write_memory_file本身与自动提取流程也要区分

write_memory_file() 底层使用write_text，同一路径可以覆盖写入。
但正常自动提取流程，会先经过should_store_memory，挡住同名候选。

所以不能看到底层能写文件，就认为自动提取已经支持正确更新旧偏好。

整理提示虽然要求应用较新的纠正，但文件没有专门的更新时间字段，
也没有完整的版本管理。因此不能完全依靠整理来可靠解决更新问题。

## 十、情况九：笔记积累到很多篇，整理成较完整的几篇

对应函数：consolidate_memories()。
可以理解为：“抽屉里的便签多了，合并一下重复内容。”

### 1. 处理前：有10篇笔记

```text
plain-language.md：讲代码要通俗。
concrete-examples.md：讲代码要举例。
before-after.md：讲代码要展示处理前后的变化。
python-tests.md：项目测试使用pytest。
……
合计10篇。
```

### 2. 什么情况下会调用整理

agent_loop() 末尾是：

```python
if extract_memories(messages):
    consolidate_memories()
```

extract_memories() 返回本轮实际新增的数量。

所以流程是：

```text
本轮至少新增1篇记忆
    ↓
调用consolidate_memories
    ↓
再检查当前总数
    ├─ 少于10篇：返回0，跳过整理模型调用。
    └─ 至少10篇：尝试整理。
```

例如：

```text
原来9篇，本轮新增1篇 → 达到10篇，可以尝试整理。
原来已经10篇，本轮新增0篇 → Agent Loop不会自动调用整理。
```

因此“达到10篇”还要结合调用入口看，不能理解为后台一直在盯着数量。

### 3. 让模型生成整理后的记录列表

这次模型收到已有记录的标题、类型、简介和正文，要求：

```text
合并重复内容。
应用较新的纠正。
删除不再有用的信息。
保留明确的用户偏好。
返回整理后的JSON记录列表。
```

假设整理结果中有：

```text
learning-style：
  通俗讲解，多给具体例子，展示处理前后的变化。

python-tests：
  使用pytest，新增功能补测试。
```

整理前后的文件可能是：

```text
之前：
  plain-language.md
  concrete-examples.md
  before-after.md
  python-tests.md
  ……

之后：
  learning-style.md
  python-tests.md
  ……
```

文件数不一定固定减少多少，取决于模型的整理结果。

### 4. 先检查新列表，再替换旧文件

程序不会一收到模型输出就立刻删除全部旧文件。
它先解析数组、过滤字段不合格的记录，并检查：

```text
整理结果不能是空列表。
新记录转换成文件名后，不能互相重复。
```

通过之后，才保存旧文件内容的快照，再执行替换：

```text
读取旧文件内容到snapshot字典
    ↓
删除旧记录文件（不把MEMORY.md当普通记录删除）
    ↓
写入整理后的新记录
    ↓
重建MEMORY.md目录
```

### 5. 写入失败，尝试恢复旧文件

如果替换过程中出现异常：

```text
清理替换过程中留下的记录文件
    ↓
按snapshot重新写回原来的文件
    ↓
重建目录
```

snapshot存在当前进程内存里，用于正常异常处理中的恢复。
它不是单独落盘的备份，也不能保证断电或进程突然终止时仍可恢复。

如果恢复过程本身又遇到文件系统故障，也不能保证一定恢复成功。

### 6. 太大的记忆库会跳过这次整理

拼接后的记录文本超过20,000字符时，会跳过本次整理。
这是CONSOLIDATE_INPUT_CHAR_LIMIT的作用。

这里不会自动拆成多批整理。

提示中还要求“最多保留30条”，但当前代码没有对返回数量单独做硬截断。
学习时要区分“提示里要求模型遵守”和“Python代码强制检查”。

## 十一、情况十：挑选记忆的模型调用失败，怎么办

对应函数：keyword_memory_selection()。

### 1. 正常选择请求失败

本来要让模型选择：

```text
当前问题：讲一下Python pytest。

目录：
  0：账单资料。
  1：学习方式。
  2：Python tests使用pytest。
```

如果API调用抛出异常，会进入except，执行关键词降级。

### 2. 关键词选择怎样工作

从请求里取一些词，例如：

```text
python
pytest
```

然后查看各篇记忆的名字和简介：

```text
账单资料：没有匹配。
学习方式：可能没有匹配。
Python tests使用pytest：匹配python和pytest。
```

匹配词越多，分数越高。分数相同则按文件名排序。

最后可能选中：

```text
python-tests.md
```

之后仍按正常流程读取正文，再交给主模型。

### 3. 这不是复杂语义搜索

降级只匹配名字和简介，没有搜索所有正文。

> “讲解风格”
> “学习方式”

意思可能相关，但文字没匹配就可能找不到。
中文提词也很简单，没有完整分词和向量检索。

因此description写清楚很重要：正常模型选择和关键词降级都要用它。

### 4. 一个需要按实际代码记住的边界

```text
模型调用抛异常：
  进入关键词降级。

模型成功返回“not JSON”等不含可识别数组的文字：
  extract_json_array() 返回 []。
  select_relevant_memories() 可能直接得到空选择。
  不会因为这个情况自动进入关键词降级。
```

原因是extract_json_array()遇到解析不了的内容，会尝试继续寻找数组，
最终找不到就返回[]，没有把这个情况抛成异常。

所以不能记成“只要选择结果不正确，就一定关键词补救”。

## 十二、四种记忆类型，分别适合保存什么

| 类型 | 保存什么 | 示例 |
| --- | --- | --- |
| `user` | 用户长期偏好。 | 学习代码时，希望通俗解释、多举例、展示前后变化。 |
| `feedback` | 以后仍适用的工作反馈。 | 修改代码时控制范围，避免顺手重构无关部分。 |
| `project` | 稳定的项目事实。 | 这个项目使用pytest；认证接口位于某个模块。 |
| `reference` | 外部资料或查找线索。 | 部署文档在docs/deploy.md；某类问题记录在指定资料库。 |

注意：

```text
记忆里的type="user"：笔记分类。
消息里的role="user"：对话角色。
```

两者虽然都写user，作用不同。

工具结果也使用role="user"，因此不能看到user就直接当成用户的长期偏好。
本节message_text()在内容是块列表时只抽取text块，普通tool_result块不会作为文本提取。

## 十三、把所有场景放回一轮任务的执行顺序

```text
用户提交一个新请求
    ↓
load_memories(messages)
  根据近期用户文字和记忆简介选择记录，再读取选中的文件内容
    ↓
build_system(relevant_memories)
  拼接基本规则、完整记忆目录、选中的记忆内容
    ↓
开始主模型与工具循环
    │
    ├─ 模型要求读文件
    │    → 程序读取，把结果追加到messages
    │    → 再请求主模型
    │
    ├─ 模型要求修改或测试
    │    → 程序执行，把结果追加到messages
    │    → 再请求主模型
    │
    └─ 模型形成最终回答，不再调用工具
         ↓
       触发Stop Hook
         ├─ Hook要求继续 → 加入对应消息，继续循环。
         └─ 没有要求继续 → 开始提取记忆。
                             ↓
                         extract_memories
                           → 获取候选
                           → 检查格式和持久性
                           → 过滤临时信息和重复内容
                           → 写入合格记录，重建目录
                             ↓
                         如果本轮新增过记忆
                           → 调用consolidate_memories
                           → 达到数量阈值才尝试整理
                             ↓
                         返回，本轮结束
```

### 1. 召回频率和提取频率要分开

```text
召回：在这次agent_loop开始时执行一次。
提取：在这次agent_loop准备结束时执行。
```

本轮内部每次工具返回后，不会自动重新选择一批记忆。
system在while之前组装，本轮后续模型调用继续使用这份system。
下一次用户发来请求，再重新召回。

CLI会在agent_loop返回后打印最终文本。
因此这里的“回答结束后提取”，准确说是模型已经生成最终回答、准备结束这轮；
不是另起一个后台线程，在用户看到回答以后异步保存。

### 2. 这几次模型调用分别在做什么

有旧记忆、无工具调用、也不需要整理时，一轮可能是：

```text
选择记忆的模型调用。
主模型回答的调用。
提取记忆的模型调用。
```

如果本轮新增后达到整理条件，还会多一次整理调用。
如果需要多次工具操作，主模型调用也会增加。
如果没有可用旧记忆，选择模型调用可以跳过。

所以“保存记忆”有额外调用成本，不是Python执行完就免费理解了全部对话。

## 十四、长度限制：为什么不能理解成“所有话都会被记住”

### 1. 召回选择使用哪段用户文字

recent_user_text() 默认取最近最多3条有文字的user消息：

```text
倒着找最近的user文字。
找到最多3条后，恢复先后顺序拼起来。
最后只保留前4,000字符。
```

普通工具结果块不产生这里需要的text，所以通常会被跳过。

因为使用的是最近几条，而不一定只有最新一句，之前的用户话也可能影响选择。

### 2. 选择模型看到的记忆目录

标题和简介拼成的目录只取前12,000字符。
大规模记忆库中的后半段目录可能没有进入这次选择请求。

### 3. 真正加载的记忆文件内容

最多选择5篇，合计文件内容预算20,000字符。
这和前面用于选择的“目录长度”是两个不同限制。

build_system()读取的完整MEMORY.md没有在此处同样裁成20,000字符。
因此“召回正文有预算”不等于“整个系统提示有同样预算”。

### 4. 提取长期记忆时看哪段对话

dialogue_text()：

```text
先取messages最后12条。
再从这些消息中提取文本。
拼接后只保留前8,000字符。
```

注意是最后12条消息，不是最后12轮用户对话。
一次读取文件就可能增加模型调用消息和工具结果消息，消耗其中的位置。

例如用户的偏好说在很早的位置，后面连续执行了许多工具，
那句话可能已经不在最后12条里，本轮提取就未必能看到它。

### 5. 整理旧记忆的输入

待整理的记录文本超过20,000字符，本次整理直接跳过。

这些都是教学实现中控制成本和规模的简化措施。
长期记忆是选择性保存的信息，不能当成完整对话的无损备份。

## 十五、失败分支和实现边界

### 1. 提取模型失败

extract_memories() 捕获异常，打印“提取跳过”的信息，并返回0。
当前轮不会因为正常捕获的提取异常继续进入整理。

如果一批候选已经成功写入一部分，随后写入失败，之前写入的文件可能仍保留。
提取流程没有给整批写入实现同样的整体回滚。

### 2. 整理模型返回空列表或文件名重复

检查不通过，跳过整理，不会为了接受空列表而先删掉原记录。

### 3. 整理替换文件时失败

按内存快照尝试恢复旧记录，重新生成目录。
这不等于完整的数据库事务，也没有处理所有并发和崩溃情况。

### 4. 用户更新偏好

同名候选会被去重检查挡住，当前实现没有可靠的自动更新流程。
记录也没有专用的更新时间、版本或有效期字段。

### 5. 与s08的关系

s08：管理当前会话的上下文预算。
s09：保存与召回以后仍可能有用的知识。

这份s09代码没有接入s08的压缩器。
记忆也不会自动替代上下文压缩，两种能力可以在更完整的系统中配合。

## 十六、把一次跨会话变化完整走一遍

第一次会话：

```text
用户：以后讲代码，要通俗、多举例、展示前后变化。
    ↓
当前任务正常回答。
    ↓
提取模型提出learning-style候选。
    ↓
Python检查：字段完整、persistent、非临时、非重复。
    ↓
写入learning-style.md，更新MEMORY.md。
```

退出程序：

```text
当前进程的history结束。
磁盘上的.memory/文件保留。
```

第二次会话：

```text
用户：带我学习Python装饰器。
    ↓
选择模型根据当前请求和记忆简介选中learning-style。
    ↓
Python读取正文，build_system把它加入背景。
    ↓
主模型看到当前问题 + 旧的讲解偏好。
    ↓
用通俗例子展示装饰器处理前后的变化。
```

如果第二次会话说：

> “这次只用一句话解释装饰器。”

则当前具体要求优先，这次应简短；不能让旧偏好覆盖当前请求。

## 十七、函数和参数速查

| 函数 | 作用 |
| --- | --- |
| `agent_loop` | 开始读笔记；中间调用模型和工具；结束提取长期记忆。 |
| `extract_memories` | 从近期对话获取候选，检查后写入，返回新增数量。 |
| `validate_memory_record` | 检查候选字段、类型和scope格式。 |
| `should_store_memory` | 检查是否persistent、是否临时、是否重复。 |
| `write_memory_file` | 保存一篇记忆文件，再重建目录。 |
| `memory_document` / `parse_frontmatter` | 在“标题等小标签 + 正文”和文件文本之间转换。 |
| `memory_slug` | 把名字转换为用于文件名和去重比较的形式。 |
| `rebuild_memory_index` | 根据现有记忆文件重新生成MEMORY.md。 |
| `select_relevant_memories` | 让模型从标题、简介中挑选最多5条，返回文件名。 |
| `keyword_memory_selection` | 选择过程抛异常时，用简单关键词匹配降级。 |
| `load_memories` | 读取选中文件，在正文字符预算内带回内容和来源。 |
| `build_system` | 拼接基本工作要求、记忆规则、完整目录和相关记忆内容。 |
| `consolidate_memories` | 达到条件时，让模型整理记录，校验后替换文件，失败尝试恢复。 |

**参数速查：**

| 参数或阶段 | 默认值与含义 |
| --- | --- |
| `select_relevant_memories(max_items=5)` | 最多选择5条。 |
| `recent_user_text(max_turns=3)` | 最多取最近3条有文字的user消息。 |
| recent_user_text文字上限 | 4,000字符。 |
| 选择请求中的目录上限 | 12,000字符。 |

| `dialogue_text(max_messages=12)` | 只查看最后12条消息。 |

| 提取请求中的已有目录上限 | 6,000字符。 |
| `CONSOLIDATE_THRESHOLD` | 至少10条记录才尝试整理模型调用。 |
| `CONSOLIDATE_INPUT_CHAR_LIMIT` | 待整理记录文本超过20,000字符则跳过。 |

这些限制分别用于不同阶段，不是同一个总预算。

## 十八、复习问答：用具体情况检查自己是否理解

### 问题1：没有.memory/时，还能回答当前用户的问题吗？

可以。没有旧笔记，召回为空，主模型仍然可以根据当前请求正常回答。

### 问题2：说出“以后多举例子”后，是立刻就写入记忆吗？

正常流程在本轮模型形成最终回答、Stop Hook没有要求继续后，才提取候选。
候选通过格式、持久性、临时标记和重复检查后，才写文件。
不是每一句用户输入都原样立即落盘。

### 问题3：候选里scope=current_task，格式没错，为什么不保存？

因为格式合法和适合长期保存是两件事。
current_task只属于当前任务，长期保存只接受persistent。

### 问题4：learning-style.md与MEMORY.md分别是什么？

前者是详细笔记；后者是所有笔记的一句话目录。

### 问题5：重启以后，是恢复上次完整聊天来记住偏好吗？

当前实现重新从空history开始。
程序从磁盘挑选相关记忆，读取后放进system，提供给本次主模型。

### 问题6：没选中账单笔记，主模型还可能看到它的名字吗？

可能。完整MEMORY.md仍会放进system。
看到目录中的名字和简介，不等于加载了那篇笔记全文。

### 问题7：旧记忆要求详细，这次要求一句结论，应该怎样？

本次具体请求优先，应给一句结论。
这不必意味着删除原来的长期偏好。

### 问题8：用户永久改变偏好，同名新候选会自动覆盖旧文件吗？

在正常提取流程中，同名会被should_store_memory拒绝。
当前代码没有可靠的自动更新机制，不能把去重理解成更新。

### 问题9：当前有10篇记忆，本轮没有新增，还会自动整理吗？

Agent Loop只在extract_memories返回非零时调用整理。
本轮没有新增，就不会仅因为已有10篇自动进入整理。

### 问题10：模型选记忆时返回not JSON，一定会关键词降级吗？

不一定。解析函数找不到数组会返回[]，未必抛异常。
当前代码的关键词降级挂在except中，API异常会触发；空解析结果通常不会。

### 问题11：一条用户偏好说得很早，后面做了许多工具操作，还保证被保存吗？

不保证。提取只看最后12条消息里的文本，再限制到前8,000字符。
很早的那句话可能已经不在这次提取输入里。

### 问题12：整理前的snapshot是一个永久备份文件吗？

不是。它是当前进程里的字典，保存旧文件名与旧文件内容。
用于异常处理时尝试恢复，没有独立落盘，也没有实现完整的崩溃恢复。

### 问题13：正文预算20,000字符，是否整个API请求就最多20,000字符？

不是。目录、系统规则、来源字段、JSON结构和messages等还会占空间。
不同阶段的预算需要分别理解。
