# s17 Goal Loop 学习笔记

**s17 在 Agent 准备结束回复时加了一次验收。** 主模型负责读代码、改文件、跑命令。它给出一条没有工具调用的回复时，程序检查这次任务的完成条件。条件还差一步，程序就把缺少的内容追加到同一份对话，让主模型接着做。课程源码见 [code.py](code.py)。

## 1. 用跑测试的例子走一遍

假设订单总价算错了，你想让 Agent 修完代码后跑一次指定测试。进入课程的交互界面后，可以输入这样的目标：

```text
/goal 修复订单总价计算，直到 pytest tests/test_totals.py 退出码为 0
```

`submit()` 识别出 `/goal` 后，把后面的内容存到 `GoalState.condition`，也把它作为用户消息放进 `messages[]`。前者是验收时要检查的条件，后者告诉主模型要做什么。所以输入这一行就会直接开始执行。 [目标入口](code.py#L576)

| 步骤 | 主模型或工具的动作 | 程序接下来怎么走 |
| --- | --- | --- |
| 1 | 主模型读文件、修改订单总价的计算逻辑 | 工具结果追加到对话，主模型继续工作 |
| 2 | 主模型回复「计算逻辑已修好」，这条回复没有工具调用 | 走到结束位置，第一次请判断器验收 |
| 3 | 判断器说「缺少指定测试的执行结果」 | 程序把这条理由追加到对话，主模型开始下一轮 |
| 4 | 主模型用 `bash` 运行测试，得到 `exit_code=0` | 程序把工具结果交回主模型 |
| 5 | 主模型读完测试结果，回复「三条测试都通过了」 | 第二次验收，条件满足时返回 `achieved` |

第 4 步拿到测试结果后，主模型会先收到工具输出。**到第 5 步，它给出没有工具调用的回复，才会触发第二次验收。** 如果第 4 步得到的是 `exit_code=1`，主模型也可以直接继续查失败原因、再改代码、再跑测试。只有它准备结束当前回复时，才轮到判断器。 [Agent 主循环](code.py#L681)

## 2. 判断器看到什么

`PromptGoalEvaluator` 会发起一次单独的模型调用。它收到**完成条件和最近的对话记录**。记录里可以有主模型的说明、工具名、工具参数以及工具结果。判断器这次调用没有工具可用，所有证据都来自记录。主模型和判断器可以配置成不同的模型，也可以用同一个模型分别调用。 [判断器](code.py#L218) · [模型配置](code.py#L831)

第一次验收时，如果对话只记着「已经修改代码」，判断器可能返回：

```json
{
  "ok": false,
  "reason": "还没有看到 pytest tests/test_totals.py 的执行结果。",
  "impossible": false
}
```

下一次验收时，记录里已经有了类似下面的内容：

```text
[tool_use bash {"command": "pytest tests/test_totals.py"}]
[tool_result exit_code=0
3 passed in 0.12s]
```

判断器就可以返回：

```json
{
  "ok": true,
  "reason": "指定的测试命令已经运行，工具结果显示退出码为 0。",
  "impossible": false
}
```

这里有两种校验。Python 检查判断器返回的 JSON 格式，例如 `ok` 必须是布尔值，`reason` 必须是非空字符串。测试到底有没有通过，由判断器根据记录里的退出码等证据判断。提供证据的是实际执行命令的工具。因此「把代码弄好」比较难验收，而「指定测试命令退出码为 0」有明确结果可以检查。 [JSON 解析](code.py#L185) · [Shell 工具](code.py#L773)

`transcript_text()` 默认按约 24,000 个字符保留最近的完整消息。如果最新一条消息本身过长，就保留它的开头和结尾，中间插入省略标记。对话很长时，前面跑过的测试结果可能已经超出判断器看到的范围。 [对话整理](code.py#L154)

## 3. 两个 continue 分别做什么

读 `_run_query()` 时，可以先抓住末尾这两个分支。下面是保留关键步骤的简化代码：

```python
if tool_results:
    self.messages.append({"role": "user", "content": tool_results})
    continue

decision = await self.goal.evaluate_after_turn(
    self.messages,
    background_running=self.background_running(),
)
if decision.action == "block":
    # 源码在这里把目标和判断器的理由追加到 messages
    continue

# 其余结果会结束这次请求
```

第一个 `continue` 把刚执行完的工具结果交回主模型。例如「测试命令退出码为 1，某个断言失败」，主模型可以据此接着修。

第二个 `continue` 把验收时发现的缺口交回主模型。例如「你汇报代码改完了，但还缺指定测试的结果」。程序把类似下面的内容加入原来的对话，消息角色是 `user`，内容由程序生成：

```text
[Goal still active]
Condition: 修复订单总价计算，直到 pytest tests/test_totals.py 退出码为 0
Evaluator: 还没有看到 pytest tests/test_totals.py 的执行结果。
Continue working and surface the missing evidence.
```

**自动续做就是把这段反馈写进同一个 `messages[]`，然后回到原来的 `while` 循环。** 主模型能看到刚才读过和改过的内容，用户也无需再输入「继续」。源码里的日常 `Stop` hook 会在准备返回时打印工具调用统计，目标验收则由此前的 `evaluate_after_turn()` 完成。 [两个分支的位置](code.py#L733) · [统计输出](code.py#L650)

## 4. 哪些情况会停下来

**一次请求返回后，目标可能仍然活跃。** 例如判断器的 API 暂时不可用，这次请求会停止自动续轮，用户可以稍后补一句「继续」，沿用原来的目标。

| 情况 | 状态 | 程序的动作 | 活跃目标 |
| --- | --- | --- | --- |
| 当前没设目标 | `allow` | 直接返回主模型的回复 | 无 |
| 还缺证据，有机会完成 | `block` | 把理由发回主模型，继续同一次请求 | 保留 |
| 条件已满足 | `achieved` | 记录成功并返回 | 清除 |
| 判断器认为目标无法完成 | `failed` | 记录失败并返回 | 清除 |
| 判断器调用失败，或返回的 JSON 格式不合格 | `error` | 返回错误原因 | 保留 |
| 连续需要阻止结束的次数超过上限 | `limit` | 结束这次请求，把控制权交回用户 | 保留 |
| 主模型调用次数达到配置的限制 | `max_turns` | 结束这次请求 | 保留已有目标 |
| 宿主报告后台工作仍在运行 | `defer` | 暂缓验收，先返回 | 保留 |

测试退出码为 `1`，通常表示还有失败要修，程序可以继续。比如目标要求使用某份已确认无法获得的测试数据时，判断器才可能返回 `ok=false`、`impossible=true`，程序把目标标为 `failed`。 [验收决策](code.py#L360)

### 两种上限怎么算

- **`block_cap` 计数的是连续需要阻止结束的次数。** 默认值是 8。假设设置成 2，前两次判断「还没做完」会各自动继续一次。第三次仍判断未完成时，返回 `limit`。这时已经做了三次验收，自动续做了两次。下一条正常用户请求会重置这个连续计数，仍可沿用目标。
- **`MAX_TURNS` 计数的是一次请求里的主模型调用次数。** 假如主模型连续三轮分别要求读文件、改文件和跑测试，就已经计了三轮。因为这三条回复都在请求工具，此时还没有进行目标验收。CLI 默认不设轮次上限，可以用正整数配置。

两项限制分别在控制器判断后、主循环发起下一次主模型调用前检查。 [拦截次数检查](code.py#L413) · [主模型轮次检查](code.py#L681) · [CLI 配置读取](code.py#L853)

## 5. 后台完成以后怎样接着做

假设宿主把测试放到后台运行。主模型先回复「测试还在跑」，此时宿主的 `background_running()` 返回 `True`，控制器给出 `defer`。这次请求返回，目标保留，判断器也还没有被调用。

后台测试结束后，宿主更新运行状态，再调用 `submit_background_result("pytest: 3 passed; exit_code=0")`。程序把结果加进原来的对话：

```text
[Background task completed]
pytest: 3 passed; exit_code=0
```

有活跃目标时，这个入口会重新运行主循环。主模型先看到后台结果，等它再次给出没有工具调用的回复，判断器就有机会根据新证据验收。课程的独立 CLI 默认把后台运行状态设为 `False`。这个例子展示的是宿主可以怎样接入后台任务系统。 [后台状态和回调入口](code.py#L545) · [提交后台结果](code.py#L665)

## 6. 怎样查看目标以及能否恢复

| 输入 | 效果 |
| --- | --- |
| `/goal` | 查看活跃条件、耗时、成功得到判断结果的次数、主模型 token 用量和最近的判断理由。上一目标已经达成或失败时，会显示该结果 |
| `/goal 新的完成条件` | 替换旧目标，马上按新条件开始执行 |
| `/goal clear` | 清除活跃目标。也可以输入 `/goal cancel` |

例如遇到 `limit` 后，可以先输入 `/goal` 看看缺什么，再发一条正常消息「测试数据已经准备好了，继续跑指定测试」。程序会保存这条补充信息，并用同一个活跃目标继续。 [状态查询](code.py#L335) · [命令入口](code.py#L576)

目标和对话默认存在当前 `AgentSession` 的内存里，因此同一个交互会话可以跨多次输入沿用目标。CLI 重启会创建新会话。如果宿主另外保存了 `goal_status` 事件，可以调用 `GoalController.restore()` 恢复最近仍然活跃的目标条件。恢复后的轮次、时间和 token 统计重新计算，完整对话由宿主另行保存和恢复。 [事件记录和恢复](code.py#L430) · [CLI 入口](code.py#L870)

## 7. s16 和 s17 怎样配合

- **s16 管工作流怎么执行。** 例如一次代码审查按正确性、安全、性能和风格拆分，并行执行，复核后汇总。
- **s17 管整件事什么时候交付。** 例如用户要求「修掉审查发现的高优先级问题，并让订单测试通过」，工作流返回「有一个高优先级问题」后，整件事还要修复和验证。如果宿主把审查结果放回对话，判断器就可以根据目标要求主模型继续。

同一件事可以先用 s16 得到审查结果，再用 s17 检查最终交付条件。两节课也可以各自单独运行。 [s16 学习笔记](../s16_workflow_runtime/note.md)

**1. Agent 刚跑完测试，判断器立刻出场吗？** 工具结果先交回主模型。等主模型给出一条没有工具调用的回复，程序才检查目标。

**2. 主模型说「已经修好了」就够了吗？** 看目标要求的证据。比如目标明确要求指定测试通过，判断器就需要从记录里找到对应的结果。

**3. 判断器说缺少测试输出，主模型怎样知道？** 程序把判断理由追加到原来的 `messages[]`，下一次模型调用会读到它。

**4. 达到 `limit` 后，目标还在吗？** 在。你可以补充信息再继续，也可以输入 `/goal clear` 清除目标。

**5. 后台任务结束，再次验收前会发生什么？** 宿主先把结果追加到对话，主模型先处理这条消息。等主模型下一次准备结束时，才进入验收。

讲解时在临时目录中使用预设的模型回复和真实的 `unittest` 命令做过演示。一次用户请求里，第一次验收发现缺少命令结果，程序自动续做。第二次验收查看到 `exit_code=0`，最终返回 `achieved`。演示共发起三次主模型调用和两次判断器调用。
